# 时机系数规格 v0.1

> **2026-11-10 用户改版（覆盖下文公式）**：`f(t) = 1.2 ^ (E[N(t)]−1)`（`E[N]`=TimingWeights.json 的
> `Expected` 列；与连接箭头 `×1.2^(n−1)` 同族指数累乘）。旧 `f = min(E[N], Cutoff)` 线性封顶废止；
> `OnTurnStart` 仍为 0（系统专用），主动三档 `E[N]=0 → f=1`（现付不进时序）。下文公式/示例保留作
> v0.1 设计沿革，施工与验收以本行为准。

> 2026-11-10 定案。范围：**效果「什么时候生效」这一层的费用系数**，即触发式效果挂在某个时机上时，效果面价要乘多少。
>
> 与相邻两层的关系（三层串联，不要混）：
>
> | 层 | 决定什么 | 真源 |
> |---|---|---|
> | 原子价 | 一次结算值多少 | 原子表 `Tier`（`P = Base + Slope × d`，见 ValueSystemConfig `AtomTier` 段） |
> | **时机系数** | 这一次结算能兑现几次 | **本文件 + `Assets/Configs/TimingWeights.json`** |
> | 卡层 | 底盘/结构/身材 | CardComposition / CardCostService |
>
> 卡费 = `Σ 原子价 × 时机系数 + 耐久费(0.5 × D) + 卡层`。

## 0. 结论先行

1. **时机系数 = 等效法术次数**。一张法术 = 立即、必然、一次 = `1.00`，是唯一锚点。
2. **公式只有一条**：`f(t) = min(E[N(t)], Cutoff)`，`Cutoff = Base = 3`。
3. **单次档看概率，多次档看密度**，两者统一到「期望兑现次数 E[N]」。
4. **次数不再是耐久费的赠品**：触发一次扣 `D × DurabilitySharePerTrigger`（= D/3）耐久，使 D 点耐久恰好兑现 3 次，与 D 无关——这样系数才能只依赖时机。
5. 攻/守/横置族的次数池是**横置**而非耐久，封顶用 `Lc = 3`（数值同 3，语义不同）。

## 1. 公式

```
E[N(t)] =
   单次档（Once）：        p(t)                 事件在宿主生命周期内发生的概率
   周期/观察族（Repeat）： λ(t) × L             每回合事件数 × 结界存活回合
   攻/守/横置族：          λ(t) × Lc            每回合事件数 × 生物存活回合

f(t) = min( E[N(t)], Cutoff ) / 1
```

- **除项 1**：一次法术结算。所以 `f = 3` 表示「相当于 3 张法术的钱」。
- **封顶 Cutoff**：期望超过 3 次的部分不再加价——因为耐久只能兑现 3 次（见 §4）。封顶值 `Cutoff` 与典型耐久 `Base` 同值，进表可调。
- **主动（Activate_*）恒 1.0**：发动时现付，不进时序。
- **OnTurnStart 禁用**（`Factor = 0`）：回合开始已收归系统专用，效果时点不准挂；玩家侧由 `OnStandbyPhase` 承接。

## 2. 参数与基准

| 参数 | 含义 | 初值 | 出处 / 校准 |
|---|---|---|---|
| `Base` | 典型耐久（次数天花板） | 3.0 | 进表可调；与卡表 `durability` 分布对齐 |
| `Cutoff` | f 封顶 | 3.0 | 与 Base 同值 |
| `DurabilitySharePerTrigger` | 每次触发消耗的耐久比例 | 1/3 | D × 1/3 = 1 次触发；D=3 时等价旧的每次 −1 |
| `λ(t)` | 每回合该时点事件数 | 见权重表 | 规则上限初值；实测见 §6 |
| `L` | 结界存活回合 | 4 | 耐久 3，每触发 −1 |
| `Lc` | 生物存活回合 | 3 | 进场→离场回合差 |
| `p(t)` | 单次事件一局发生概率 | 0.12–1.00 | 事件数 ÷ 机会数 |

`λ` 的规则初值（可直接用，不必先测）：

```
OnStandbyPhase / OnTurnEnd   = 1.0   每回合一次
OnPhaseStart / OnPhaseEnd    = 3.0   准备 / 主 / 战斗
OnDraw                       = 1.2   系统抽 1 + 效果抽牌 0.2
OnCardPlayed / Settled       = 2.0   每回合出 2 张
OnDealDamage / OnTakeDamage  = 1.5   战斗 1 + 效果伤害 0.5
OnAttack / OnAttacked        = 1.0   横置限频
OnAtomicEffect*              = 4.0   每张牌 1–2 原子
OnScry                       = 0.15
```

## 3. 权重表

全量 35 行在 [`Assets/Configs/TimingWeights.json`](../Assets/Configs/TimingWeights.json)，本文件只摘录分组结论：

| 分组 | 行数 | f 分布 |
|---|---|---|
| `Once` 单次 | 8 | 0.12 – 1.00（p 直接作系数） |
| `Repeat` 周期/观察 | 18 | 0.60 – 3.00（λ×4 封顶 3） |
| `TapAnchored` 攻/守/横置 | 5 | 0.90 – 3.00（λ×3 封顶 3） |
| `Active` 主动 | 3 | 恒 1.00 |
| `Disabled` 禁用 | 1 | 0（OnTurnStart） |

`Bucket` 列只用于**兜底归类与宿主校验**，不参与计算；计算只读 `Factor`。这保证「系数只依赖时机」——同一时机在任何卡上都是同一个数。

## 4. 耐久消耗新口径

**旧口径**：触发一次 −1 点耐久，D 点耐久 = D 次。

**新口径**：触发一次消耗 `D × DurabilitySharePerTrigger`（= D/3），**D 点耐久恒兑现 3 次**。

| D | 每次触发消耗 | 次数 | 角色 |
|---|---|---|---|
| 1 | 0.33 | 3 | 极脆，但很能撑触发 |
| 3 | 1.00 | 3 | 标准（与旧口径等价） |
| 6 | 2.00 | 3 | 很耐打，但触发次数不变 |

这样 `D` 只表达「血量」，`Cutoff` 只表达「次数」——两个自由度不再互相污染。

**受伤扣耐久不变**：`ApplyDamage` 按实际伤害点数 1:1 扣（[KeywordRules.cs](../Assets/Scripts/HotUpdate/CardCore/Attribute/KeywordRules.cs#L486)），不受本口径影响。

### 实现约束

耐久层是 int（`CounterRules.DurabilityCounter`），`D/3` 不是整数。**不要改耐久为 float**，用「触发累计」：

- 每张结界卡上记一个触发计数（卡字段或隐藏指示物，不入快照可见面）；
- 每满 3 次触发，扣 `D` 点耐久并清零计数；
- 效果按每次触发照常结算，不因计数未满而推迟。

等价语义、零耐久类型改动。计数需进网络快照（否则客机与主机扣耐久时点不一致）。

## 6. 校准（λ 实测）

规则初值足够上表，但 `λ` 必须用真实对局校准。Method：

1. 跑一批脚本对局（TideSim `--games 200 --matchup all`）；
2. MatchLog 逐局统计 11 类事件计数与「生物/结界进场→离场回合差」；
3. 每时机 `λ_实测 = 事件总数 ÷ 总回合数`，替换权重表 `Lambda`，`Expected/ Factor` 按公式重算；
4. 验证器输出「λ 初值 vs λ 实测」差异表，差异 > 30% 的时机人工复核。

统计脚本待写（`tide_rl/tools/timing_lambda_stats.py` 或 TideSim 导出侧扩展）。

## 7. 与旧口径的差异

| | 旧（2026-11-05 两档 ×1） | 新（本规格） |
|---|---|---|
| 周期时机系数 | 恒 1.0 | 0.6 – 3.0 |
| 次数由谁付款 | 耐久（每点 0.5 蓝，兼作次数价） | 时机系数（次数） + 耐久（血量）两条腿 |
| 触发消耗 | 1 点/次 | D/3 点/次 |
| 生物挂周期时机 | 装载期拒绝 | 不变（仍拒绝，宿主规则不动） |

**影响面**：挂周期时机的结界普涨 2–3 倍（f 从 1 到 3）。这是补收，不是回归——但对现有预组是实打实的涨价，落地时建议先只改**定价显示**、跑几局看卡费曲线，确认不顶穿预组预算后再切实际生效。

### 落地状态（2026-11-10 段 2b 已切正）

**影子开关已删除**：`TimingCostFactorOf` 直接读行 `Factor`、`ConsumeTriggerDurabilityShare` 直接走 `D/3` 累计——不保留旧口径分支。缺行/表不可读才回落 `TimingFactor` 桶（安全侧兜底）。

## 8. 后续：ValueSystemConfig 结构化迁移

本规格的权重表刻意**不放进** `ValueSystemConfig.json`：它是 35 行 × 6 列的**数据表**，KV 反射（每列一个 C# 字段）不合适。

`ValueSystemConfig.json` 自身计划迁到结构化格式（`{ "CardCost": {...}, "TimingFactor": {...} }` + `TideJson` 整体反序列化），届时只保留「section → Config 类」一层映射，字段级不再反射。本表可作为该格式的 `TimingWeight` section 并入，也可保持独立文件——两者不冲突。

## 9. 风险

1. **Cutoff 与 Base 耦合**：两者都写 3，改一个必须同时看另一个（`Cutoff` 是次数，`Base` 是耐久点）。
2. **D≠3 的卡**：次数固定 3，D 只影响血量；D=1 的结界会变成「很能撑触发」的怪卡，需要内容侧单独审。
3. **λ 偏差**：规则初值是估计值，实测前所有 f 都有 ±30% 误差。
4. **与 30 闸/过载无关**：过载（每卡 30 次）是硬保底，不参与定价，不要把它写进本公式。
