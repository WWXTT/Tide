> 口径：模型执绿（`modelTheme=green`）对脚本红，胜率恒 0。本文只做两件事：
> ① 固定已确认的结论与证据；② 把还没判定的二义、以及要改的地方写成可验收的阶段计划。

## 0. 摘要

**已确认（可据此停掉旧结论）**

1. **红绿 0% 不是模型策略问题**：同一执行器里，脚本绿对脚本红同样 0/400（见 C1）。
   → 撤回「模型执绿比裸脚本差 41pp」；「先查模型侧 T5/T7 链路」这条线索降级为次要。
2. **§0.2 的 41% 基线只在 TideSim 口径成立**，headless 执行器不可复现（见 C2）。
3. **1c 的红镜像回退是实锤**，且发生在续训的头 5 万步内，首要嫌疑是 hot-restart 的 LR/Adam 重置（见 C3）。
4. **A2 三发对照判定根因方向：(ii) headless 驱动把绿削掉了**（2026-11-22 实测，主仓 200 局/发，
   全部 LifeZero 自然终局、0 判和、0 环境重启；见 C7 与 V1/V2 判定块）。

5. **根因已定位并修复验证：英雄技能卡不一致**（2026-11-22 19:44~20:00，D2a；见 C7-b）。
   `ThemeDecks()` 丢掉预组 `skillCardId`，driver 回落 `AutoPickSkillCard`（卡组内最低锚价法术），
   于是红「激励」/绿「牺牲」/蓝「蛰伏」**从未进入 headless 对局**（TideSim/挑战/联机一直是对的）。
   单变量对照（只改技能，其余不动）：绿对红 **0/400 → 79/200 = 39.5%**（TideSim 41%）、
   绿镜像 P1 **12% → 97.8%**（TideSim 92.5%）、绿对蓝 8.5% → 56.5%；红镜像几乎不动（对照）。
   → 旧结论「绿对红 0% 是结构性问题」作废；**训练环境同源，1b/1c 权重按 §5 属换环境须重训**。

### C7-b 根因：英雄技能卡不一致（已定位、已修复、已单变量验证）

**机制链条（代码级）**

1. `BattleDeckSources.ThemeDecks()` 只返回 `(key, List<CardData> deck)`，**丢掉了预组 JSON 里的
   `DeckData.skillCardId`**（红 `C_77A047CD` 激励 / 绿 `C_AC7FC01F` 牺牲 / 蓝 `C_23EE2486` 蛰伏）。
2. `TideHeadlessDriver.Reset(...)` 旧签名没有 `skillCardId` 形参 → 一律走
   `skillCardId1: HeroSkillSystem.AutoPickSkillCard(deck1)`（"卡组内锚价最低的合格法术"）。
3. 对比 TideSim `DeckSim` 显式传 `SkillCardId1/2`、挑战/联机走 `BattleController(mySkillCardId)` ——
   **只有 headless 训练/评估口径在猜技能**。这就是"同一份 CardCore、两个执行器结论不同"的全部来源。
4. 后果：绿套没有「牺牲」→ 无 Any 产出 → T5 阿格洛斯线断；蓝套没有「蛰伏」→ 充盈踩不到档；
   红套没有「激励」→ 仅靠卡组强度硬打（所以红镜像表现反而"正常"，掩盖了问题）。

**修复（D2a，2026-11-22）**：`ThemeDecksWithSkills()` 带回 `skillCardId`；
`ResetScriptGame/Reset` 增 `skillCardId1/2` 形参；server 三条路径（script / simpleai / selfplay）
逐侧传各自的正牌技能；两仓已同步（19:40，文件 size 一致）。

**单变量验证（只改技能，卡组/规则/驱动不动；200 局/发）**

|---|---|---|---|---|
| 绿 → 红 | **0/400（0%）** | **79/200 = 39.5%** | 41% | **回到基线** |
| 绿 → 蓝 | 17/200 = 8.5% | **113/200 = 56.5%** | 62.5%（CSV 直算 47.5%） | 回到基线区间 |
| 绿镜像（P1） | 11/92 = 12.0% | **89/91 = 97.8%** | 92.5% | **极性反转消失** |
| 红镜像（P1） | 36/99 = 36.4% | 38/112 = 33.9% | 36.0% | 未动（对照成立） |
| 红 → 蓝 | 143/200 = 71.5% | 132/200 = 66.0% | 74.5% | 小幅下移，同量级 |

- post-fix 跑在 `Tide_train` 副本（其 CardCore 比主仓旧 9 个文件）→ 与 11-18 的 TideSim 基线同代，
  可比性反而更强。
- 绿对红 39.5% 与基线 41% 差 1.5pp（n=200 的 95% 区间约 ±6.9pp）→ **技能修复即回到基线**，
  不需要再引入"卡组平衡"或"驱动结构"解释。
- 红 → 绿 还在跑（见 §5 附录的最新一次），其余格（蓝→红/蓝→绿/蓝镜）尚未重测。

**连带作废的结论**

1. 「绿对红 0% 是结构性问题」→ 作废（是技能配置错）。
2. `train_tide_complete.py` 的 `SCRIPT_MATRIX_BASELINES`（B4 选点基线）全是 pre-fix 病态值
   （green|red=0、blue|green=0.93）→ 必须换 dfix 值，否则 `best` 继续选错。
3. 6 格 TideSim 门槛表、18 格矩阵表都要按新口径重测。
4. **1b/1c 全部权重作废**：训练环境同一驱动，模型和脚本双方都没有正牌技能
   → 按 `AI训练说明.md` §5「换环境须重训」，D2a 属换环境。
5. 行为指标的历史解释同步作废：`sacrifice_rows` 等统计口径下的"英雄技能行"其实是错技能的行。

**⑤ 新主标尺建议（待用户拍板）**

- 记 `Δ格 = 模型同格胜率 − 脚本同格胜率`（同执行器、同批次、配对）。

## 2. 待验证（按判别力排序）

### V1 绿对蓝对照 —— 判定 (i)/(ii) 【最高优先】

- 假设：若 headless 驱动的脚本侧绿是完好的，绿对蓝应接近 TideSim 口径（绿 62.5%）。
- 实验：`script_vs_script.py --episodes 200 --model-theme green --theme blue`。
- 判据：
  - 绿对蓝 **≥ 55%** → (i) 成立：驱动没问题，红在这个执行器里就是压死绿 → 转 V3；
  - 绿对蓝 **≤ 5%** → (ii) 成立：脚本侧绿整体不可赢 → 转 D 阶段（驱动保真度）。
- 成本：约 2 分钟（含 Unity 启动约 3~5 分钟）。
- **判定（2026-11-22 实测，主仓 200 局）**：**8.5%**（17/183，P1 6.8% / P2 10.3%，全 LifeZero）

- **教学暂停 = 闸门 + 让出点两件事**：
  1. 闸门：`GameStateManager.Pause(reason)` 只切状态；真正拦动作的是
     `GameCore.Update` 的 `if (!CanPerformGameActions || PresentationHoldCount > 0) return;`
     （`GameCore.cs` L784）+ UI 输入两处短路（`BattleScreen.Fans` L170/L432）。
  2. 让出点：真正让 AI 停在中途的是 `SimpleAI.PacingWait`（`public Func<UniTask>`）——
     教学导演注入 `WaitVisualsIdleAsync + 2 帧稳定拍`（`BattleTutorialDirector.cs` L675-691），
     AI 每两个动作之间 `await PacingWait()`；暂停期该 wait 不返回 → AI 卡在那一步。
     **不是把回合状态机存起来**。
- **headless 为什么用不了**：`PaceAsync`/`StageHoldAsync` 首行 `if (PacingWait == null) return;`
  —— 驱动从未注入 `PacingWait`，batchmode 里这些 await **同步直通**，脚本回合一口气跑完，
  中途没有让出点。此时设 `Paused` 只能让动作被拒，交不回控制权，还可能把回合卡死半路。
- **可复用的两件**：
  1. `SimpleAI.PacingWait` 注入点（本就是"动作之间插桩"的口，**不用重写 SimpleAI 内部**）；
  2. `GameStateManager.Pause` + `CanPerformGameActions` 闸门（暂停期拒绝落地动作，不用另写）。
- **唯一缺口 = 驱动的阻塞调用**：`RunSimpleAiTurn` 的 `TakeTurn = TakeTurnAsync().GetAwaiter().GetResult()`
  阻塞期间无法返回 Python。两条路：
  - **(a1) 非阻塞泵**：脚本回合跑成可轮询 UniTask，在 `Main` 循环推进。风险：batchmode 下
    `UniTask.Yield()` 依赖 player loop，而 `Main` 阻塞时 loop 不 tick → 可能泵不动。
  - **(a2) 工作线程 + 阻塞式让出**：headless 的 await 本就同步完成、不依赖 player loop，
    可把脚本回合放 worker 线程，`PacingWait` 实现为「存待决策 → 阻塞等信号」，主循环照常服务 socket。
    线程安全可控（同一时刻只有一个线程碰引擎）。

**Spike（先做，半天）——判据**

- 目标：验证 worker 线程 + 阻塞式 `PacingWait` 能否在 batchmode 里把脚本回合**停住并恢复**。
- 判据：20 局脚本对局（固定 seat/seed，用 B1 的种子钉死），要求
  ① 能在第 N 个动作处停住；② 外部信号后继续跑完；③ **最终 (winner, turn) 与不停版本逐位一致**。
- 分支：成功 → 工期落到 **1~2 天**（改 `RunSimpleAiTurn` + 注入 PacingWait + 全回归）；
  失败 → 回状态机方案，工期按 2~5 天算。

## 3.5 行为辅助校验（用户口径 v0.1，2026-11-22）——辅助层，**不是主标尺**

### 3.5.1 定位（2026-11-22 用户拍板）

**胜率是验证主标尺**，本节三条行为指标只作**辅助佐证**：判断「AI 确实学到了这套预组的打法，
不是乱打」，以及当胜率读不出原因时做归因分流。**不设通过门槛、不作为验收阻断项。**

用途只有两个：

1. **归因分流**（胜率 → 行为）：

   | 胜率 | 招牌线 | 判读 |
   |---|---|---|
   | 低 | 完全不发动 | 没学会 / 环境根本不允许（先查环境，别急着归因到策略） |
   | 低 | 发动了但转化不了 | 学会了但赢不下来 → 卡组强度 / 环境压制 |
   | 高 | 发动 | 真学会 |
   | 高 | 不发动 | **警报：赢法可疑**（靠对手弱 / 退化打法），需要人工看盘 |

2. **反退化监控**：胜率不动但行为线偷偷归零，是「策略塌成随机打」的早期信号。

**前提：必须同执行器、同批次同时测脚本侧与模型侧**——Stage A 的教训正是「脚本绿 0/400」
才让「模型绿 0/240」从「模型学不会」改判为「谁执绿都输」。

### 3.5.2 定义（逐条已对到卡表与策略代码）

| ID | 预组 | 触发条件（每局计数） | 脚本侧实现锚点 |

| B1 | 红·快攻 | 同一回合内先「血偿」(C_E105FABA，3 费) 再「活体炸弹」(C_5705F9FE，0 费)，合计 3 费，且该回合结束对手 Life ≤ 0 | `RedAggroStrategy` 的 `bombLethal`/combo 分支（L149-152、L180-183） |

### 3.5.4 实现路径（复用 `MatchLogService`，不新造事件钩子）

- **关键发现（2026-11-22 复核）**：`MatchLogService` 已订阅 `EventManager.AnyPublished`，
  收**全部引擎事件**且逐条带 `TurnNumber / EventType / IGameEvent`，`GameCore.Reset` 自动清空
  （每局一份）。引擎侧事件类已覆盖所需：`CardPlayEvent`、`CardCastSettledEvent`、`DamageEvent`、
  `LifeChangeEvent`、`EffectActivatedEvent`、`CardPutToBattlefieldEvent`、`RoleDeathEvent`。
  → **账本不用新造**，只需要「白名单投影 + 序列化」。
- **投影**（每局 ≤300 条，超出截断并置 `truncated`）：

  | ev | 来源事件 | 记什么 |
  |---|---|---|
  | `play` | `CardPlayEvent` / `CardCastSettledEvent` | `{t, seat, card, cost}` |
  | `skill` | `EffectActivatedEvent`（源=英雄技能卡，如蛰伏 `C_23EE2486`） | `{t, seat, card, nTargets}` |
  | `summon` | `CardPutToBattlefieldEvent` | `{t, seat, card}`（B3 大哥落地） |
  | `damage` | `DamageEvent` / `LifeChangeEvent` | `{t, seat, srcCard, amount}` |
  | `fullness` | `CardCastSettledEvent` 后的 `EffectResolveEvent`（源=潮痕碑/深潭碑） | `{t, seat, srcCard}`（口径见 3.5.6） |
  | `win` | `RoleDeathEvent` / `LifeChangeEvent`→0 | `{t, seat}` |

- **落盘**：`info.events` 随 reset/终态响应回传 → Python 写 `<run>/behavior_<split>.json`。
- **顺带解决**：avg_len（C5）、绿大哥线、红双法术、蓝充盈一次覆盖，不必在 Python 侧逆向 `actions_` 特征。
- **验收**：同一局脚本侧账本计数必须与策略自带日志对得上——`预组改造方案.md` L160 的
  「200 局蛰伏 247 次」是最现成的对账基准。

### 3.5.5 使用规矩

1. **优先级**：胜率是主标尺（第一判据，且必须配对、足够局数、同执行器）；行为指标是第二层佐证，
   只在「胜率判不了」或「怀疑胜率来路不正」时出场。
2. **不设门槛**：行为指标不参与 `best` 选点、不参与 3a 验收阻断；只报数 + 按 3.5.1 的四象限归因。
3. **同执行器、同批次、双侧测**（脚本侧 + 模型侧）；单侧数字不作结论。
4. 同时记录「发生局数 / 总局数」与「每局平均次数」——只看占比会丢掉频率信息。

### 3.5.6 口径确认（2026-11-22 用户拍板）

1. **B3 归属 = 绿·慢速**（原话「蓝色 T5 召唤 14 费大生物」为笔误）；
   蓝·控制 现卡表 30 张 = 潮汐×12 / 深潭碑×8 / 乱锋×6 / 寒冬×4，无任何生物。
2. **B1 / B2 定义照本文 3.5.2 执行**（用户确认「前两条行为指标就是这个意思」）：
   「3 费 / 4 费」= 回合 T3 / T4（寒冬 6 费靠 T3 蛰伏攒费），不是卡面费用。
3. **B2 充盈判定暂按策略同款口径**：`己方剩余元素 − 对方剩余元素 ≥ 门槛(2)`

   以便日后切到「对手地全横置」口径时不丢数据。
