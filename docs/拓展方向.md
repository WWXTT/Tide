## 1. 母原则：边界编译，运行期不解释

> 玩家的一切表达，在**装载边界**被编译成引擎认识的内置形态；结算期永不解析玩家文本。

| 表达 | 编译动作 |
|---|---|
| 词条 | **早展开**：装载期展开成内置原子序列 |
| 条件 | **早解析**：装载期 parse 成 AST，结算期只求值 |
| 数值 | **早编译**：同上，且必须能静态定出上界 |

三条推论，任何方案都要满足（否则该方案不成立）：

1. **结算期零解析**：`IAtomicEffectHandler.ExecuteAsync` 及其下游不出现任何 parse。
2. **AI / 服务端只看编译产物**：观测与动作空间不需要知道"玩家写过什么"。
3. **编译失败必须在装载期暴露**：不留到对局里去炸。

## 2. 条件表达式

### 2.1 现状：两套口径，都在替你做"难度判断"

**证据：**

- `CostDerivationService.BuildGatePremium()` 返回 `Dictionary<string,int>`，内容由两半拼成：
  - **产出条件族 = 代码常量**：`DmgKillsTarget / DeclareHit / DeclareMiss / ProphecyHit / ProphecyMiss` 各 2；
  - **局面门族 = 表列直通**：遍历 `ComposerCatalog.SituationGates`，取原子表 `Budget` 列。
- 现状 13 行局面门的 `Budget` 是 1 / 2 / 3 三档：
  - 1 档：生命/卡组/生物 高于或低于对手（全部是"五五开"条件）
  - 2 档：本回合第一张卡、手牌为 0、操控地 ≥9、地 ≤3、生命 ≤7
  - 3 档：命运一抽、支付代价
- 合成器奖励上限 `RewardFilterCap` 统一封顶 5。

**问题**：`BuildGatePremium` 的两半，本质都是**设计者对"这个条件多难得"的隐式判断**。判断对了没人记得，判断错了就是平衡漏洞；而玩家新增条件时，这套判断**根本不存在**——没有地方可以填。

### 2.2 为什么预算不能由作者写

**定案**：条件 = 纯校验上限、零计价（`CostDerivation` 已有注释）。所以：

> 条件本身不产生任何费用，它唯一能影响的是 **Then 奖励的上限**。
> 因此：**概率模型就是经济模型。**

推论：**预算只能由引擎推导，不能由作者声明**。作者提供"条件是什么"，不提供"条件值多少"。

> 补充（修正一处早期说法）：预算推导**不改变卡价**，只改变"哪些奖励合法"。所以概率表不一致的后果是"同一张牌一端合法一端非法"，不是"两端价格不同"。见 §2.8。

### 2.3 作者接口：一行表，不加列

**定案**：`GateId` 从"单个条件 id"**升级为表达式串**。旧值天然是叶子，**零迁移**。

```jsonc
{
  "ID": "b7c1e2a4",
  "EnumName": "绝境",
  "DisplayName": "生命≤7 且 手牌为 0 时",
  "EffectType": "SituationGate",
  "MountKinds": "有限分支",
  "GateId": "LifeLe7 & HandEmpty",   // ← 表达式（新）
  "Budget": 0                         // ← 0 = 引擎推导（新语义）
}
```

**约束：**

- 不新增列。加列等于开第二套语法，两份 parser 必然不同步。
- `Budget > 0` 只对**内置表**有效（保留内部钉死口）；玩家内容包里的行一律必须为 0，非 0 直接拒绝装载。
- 表达式叶子只能引用**已注册的条件 id**（内置 switch 里那些），不能引用另一个玩家条件（深度恒为 1）。

### 2.4 求值接口：switch 下沉为叶子层

```
Evaluate(condRef):
  if ConditionTable.TryGet(condRef) → Eval(Parse(row.expression))
  else                              → 内置 switch（原样，一个 case 不改）

Eval(node):
  Leaf(id)   → 内置 switch
  And(a,b)   → Eval(a) && Eval(b)   // 短路
  Or(a,b)    → Eval(a) || Eval(b)
  Not(a)     → !Eval(a)
```

语法：

```
expr  := or
or    := and ( '|' and )*
and   := unary ( '&' unary )*
unary := '!' unary | '(' expr ')' | LEAF
LEAF  := [A-Za-z][A-Za-z0-9]*
```

**性质**：求值是纯函数（只读局面、无副作用、短路确定）→ 天然可回放、可服务端一致执行、可 AI 预测。

**注意**：`TargetFilterSystem.TryParseStatComparison()` 已经有一个迷你解析器（`Power>5` / `Life<=3`）。它是"标量比较"的种子，但不属于本阶段——见 §3.7。

### 2.5 概率推导

#### ① 叶子概率必须实测，且按评估时机分桶

`P(leaf | timing)`。

同一个 `HandEmpty`，在 OnPlay 与回合结束时的基准率不是一回事；用全期平均值会把两头都算错。

- 数据来源：`TideSim` 批量对局，在每个"条件被评估"的时刻采样。
- 这是本阶段唯一新增的数据资产，也是唯一可信的来源。
- 采样缺失 = 无法定价 = **拒绝装载**（不许默认 0.5，见 §2.6 第 3 条）。

#### ② 组合用区间推导，不假设独立

`生命≤7` 与 `手牌为 0` 是负相关的，按独立乘会把概率算高。改用 Fréchet 界做区间算术：

```
P(A & B) ∈ [ max(0, pA + pB − 1),  min(pA, pB) ]
P(A | B) ∈ [ max(pA, pB),         min(1, pA + pB) ]
P(!A)    = [ 1 − hi_A,             1 − lo_A ]
```

递归下去，每个子表达式得到 `[lo, hi]`。**定价取 `hi`**：概率估高 → 预算低 → 安全。宁可少给，不可多给。

#### ③ 预算公式

```
Budget = clamp( floor( K / P_hi^α ), 1, CAP )
CAP = 5        // 与合成器 RewardFilterCap 同口径
```

`K`、`α` 用现有 13 行标定（§2.5 ④），不凭空取值。

#### ④ 标定：用现有 13 行反推 K 和 α

现状手填值已经是一条很干净的曲线：

| 现有行 | Budget | 隐含 P |
|---|---|---|
| 生命值低于/高于对手、卡组低于/高于、生物低于/高于 | 1 | ≈ 0.5（五五开） |
| 本回合第一张卡、手牌为 0、操控地≥9、地≤3、生命≤7 | 2 | ≈ 0.2~0.3（待实测） |
| 命运一抽、支付代价 | 3 | ≈ 0.1（待实测） |

1 档全是"五五开"、3 档全是罕见局面——**这就是 `1/P` 的形状**。

流程：

1. 用这 13 行拟合 `K`、`α`（先取 `K≈0.5`、`α≈1` 作初值再调）。
2. 拟合完对全表跑一遍，比对"派生值 vs 手填值"。
3. 差异大的行只有两种解释：手填错了，或 `K/α` 该调。

**副产品**：这一步顺带就是存量平衡体检——偏得离谱的门，可能一直是漏洞。

### 2.6 数值校验清单

装载期一次跑完，错误定位到"行 + 字符位置"：

| # | 检查 | 处理 |
|---|---|---|
| 1 | 语法可解析、嵌套深度 ≤4、token ≤12 | 拒绝 |
| 2 | **叶子封闭**：所有叶子在内置注册集内 | 拒绝 |
| 3 | **可估**：每个叶子在概率表里有样本 | 拒绝（不许默认值） |
| 4 | **不可满足**：`hi < 0.01`（如 `A & !A`） | 拒绝 |
| 5 | **恒真**：`lo > 0.99`（如 `A \| !A`） | 拒绝（等于无条件送奖励） |
| 6 | **区间过宽**：`hi − lo > 0.5` | 告警（预算会被压到最低档） |
| 7 | **自引用**：叶子指向另一个玩家条件 | 拒绝（深度恒 1） |
| 8 | **撞名**：id 与内置/他人重名 | 拒绝（命名空间） |
| 9 | **预算区间**：落在 `[1, 5]` | 超上限截断 + 告警 |
| 10 | **奖励匹配**：Then 奖励锚价合计 ≤ 预算 | 拒绝（沿用现有校验） |

### 2.7 没有 UI，报错就是全部的产品

本阶段**不新开任何界面**。作者唯一的反馈通道就是装载报错，所以报错质量直接决定功能可用性。

**装不上**：

```
[原子表_系统] 行「绝境」(b7c1e2a4) 条件无法装载：
  叶子 "HandEmpty" 在时机 OnPlay 下没有概率样本
  → 无法推导预算，已拒绝
```

**能装但很亏**（这条尤其重要）：

```
条件区间 [0.05, 0.62]（宽度 0.57）→ 按上界 0.62 定价 → 预算 1 档
  → 建议：拆成两个条件分别挂 Then，可拿 2 + 2 档
```

作者写 `A & B` 是想要更强的奖励，结果区间一宽反而更亏；必须明确告诉他改法。

### 2.8 概率表维护与两端一致

- **概率表是新的真相源**，跟卡池与平衡走；每次大版本重测，带版本戳。
- **缺失即拒绝**，不设默认值——缺数据就是缺数据。
- **版本必须两端一致**：预算影响"奖励是否合法"，而合法性**不进内容哈希**（`ContentHasher` 只覆盖 steps/costs）。所以概率表变了以后，同一张卡可能从合法变非法却**不换号**。
  - 建议：概率表版本纳入开局握手（`NetMatchHandshake` 现有 `AtomicRowsHash` / `ContentSig` 那条路），失配显式拒绝并说明原因。
  - 不加这条，会得到"对面能用一张我这边判定为非法的牌"这种最难查的 bug。

### 2.9 本阶段不做

- 条件可视化编辑器 / 积木块
- 新 UI 界面（作者直接改 JSON）
- 标量比较叶子（`Life < 5`）——语法上留位，见 §3.7
- 玩家自定义叶子（只能组合内置叶子）

## 3. 数值表达式（方向未定）

> 状态：**方向已明，方案未拍板**。本节记录"为什么贵"、"必须拆的三层"、"可选的三档"，以及待决策清单。

### 3.1 为什么它比条件贵一个量级

`AtomicEffectInstance.Value` 是 **int，且三合一**：

> `int Value` // 唯一数值参数——名义值：**计价、描述、UI 都读它**

- 计价要静态数（构筑期算价）
- 描述要静态数（无 context 时也要能出文案）
- UI 要静态数（卡面读数）

值是局面函数时，这三件事同时失去支点。**这是结构问题，跟先做后做无关。**

### 3.2 三层字段（定案，已写入施工计划 §4.1）

| 字段 | 用途 | 谁读 |
|---|---|---|
| `Value` | **定价锚**（名义值，构筑期常量） | 计价 / 描述 / UI |
| `ValueMax` | **静态上界**（校验/告警用） | 校验器 / 平衡体检 |
| `ValueExpr` | **结算期求值**（v1 只允许取值引用，不接运算符） | `context.ResolveValue(atom)` |

### 3.3 不按上界定价（定案）

反例：活体炸弹的伤害是"参照生物的当前攻击力"，实战可达 9+；而它的定价锚显然不是 9 伤，是设计者心里的"典型值"。若按上界收，所有成长型效果都会贵到不可用。

**定案：名义值定价、上界只告警**——"这张牌上限 12 伤，超出同类分布"。

这样"价是构筑期常量"的契约仍然成立，只是常量叫**名义值**。

### 3.4 求值顺序（钉死）

```
解析 bindings（Refs）
→ 求值 ValueExpr
→ 增伤/减伤修正链
→ 按幅度掷（amp）
→ 逐目标各自掷
```

- 现有 `GetRolledValue()` 是无 context 的实例方法，**保留为常量快捷方式**。
- 新增 `EffectExecutionContext.ResolveValue(atom)`：`ValueExpr` 空 → 旧行为；非空 → 解析引用再按幅度掷。
- 迁移顺序：先只改 BurstDamage / LivingArmor 两个 handler，其余不动。

### 3.5 载体：新增列，绝不把 int 改 string

- `AtomicEffectEntry` 增加 `valueMax` / `valueExpr`（按值省略，空=不写）。
- `AtomicEffectInstance` 增加同名两字段。
- `EffectSlim` 往返 + `ContentHasher` **必须纳入**——否则同 refId 不同表达式会撞内容哈希。
- **反向操作（把 `Value` 改成 string）禁止**：那会让 P0/P1 的存量数据全线迁移，而这本可以零迁移。

### 3.6 三档表达力（**A 档已定案**）

| 档 | 形态 | 表达力 | 代价 |
|---|---|---|---|
| **A** | 纯取值引用：`ref.power` / `ref.life` / `ref.cost` / `state.lands` | 覆盖现有三个参照族特例 | 最小；已足够吃掉 BurstDamage / LivingArmor / ShieldSlam |
| **B** | 受限算术：`+ - × ÷`、`min`/`max`、常量 | 覆盖大多数"成长型"设计 | 需要"上界推导器"（区间算术求 max）+ 描述降级策略 |
| **C** | 完整表达式（含条件嵌套 `若 X 则 Y`） | 理论无上限 | **击穿构筑期定价**，等于把动态定价整套引入 |

**定案：先做 A**（覆盖三个参照族特例、不引入表达式引擎）；B 待 A 跑顺后单独评估；C 不做。
落地步骤见 `docs/地基计划_虚拟原子与数值A.md`。

理由：A 就能把现有三个特例原子吸收成"普通原子 + 参照 + 值引用"，`grep -c BurstDamage` 可以降到只剩枚举与表行——这本身就是重构的验收标准。

### 3.7 未决清单

| # | 待决问题 | 影响 |

| 2 | 是否允许运算符；允许哪些 | **A 档不接运算符（已定）**；B 档再议 |

- 值表达式只能读**公开量**。牌库顺序、对手手牌内容这类隐藏信息绝不进叶子——否则表达式立刻变成信息作弊器。
- 结算期不解析文本（§1 推论 1）。
- 身份与摘要基于规范化后的 AST（§4 第 2 条）。

## 4. 对 P0（词条 / 虚拟原子）的三条预留

这三条**现在就要有**，每条成本约一天，省的是后面一次全库重算。

### 4.1 参数绑定走 string 载体

词条展开时把 `{n}` 替换成值。若替换目标是 `int`，P2 要支持"参数 = 表达式"时展开器必须重写。

**做法**：绑定目标是 string（`{n}` → `"3"`），装载期只接受能 parse 成常量的串；将来开放叶子时不动结构。

### 4.2 身份与摘要基于规范化 AST，永不基于文本

`"a+b"` 与 `"b+a"` 是两段文本、一个 AST。按文本哈希身份，改一次格式就换号，卡组 / 存档 / 联机全断。

**做法**：parse → normalize → hash AST。seal 只覆盖**行为**（body / params / slot），不覆盖名字与风味文案。

### 4.3 语义串只存原文，装载期解析，不回写

`Domain` 已经是这么做的（文本存盘、装载解析），照此惯例即可。

**反面**：把解析结果写回存档 → 换语法就动存档。

## 6. 分期与验收

### P0 · 词条（现在做）

- 设计：已定（早展开 + 7 条词条不变量 + 内容包容器）
- 验收：同一张卡"用词条摆"与"直接摆原子"的推导价**完全相等**；`grep` 不到任何"玩家内容"的类型判断

### P1 · 条件表达式

1. 叶子概率表 + TideSim 采样脚本（先有数据，否则后面空转）
2. 布尔表达式解析器（只有 `& | !` 与括号）
3. 区间推导 + 预算公式 + 用 13 行标定
4. 十条校验
5. 作者文档 + 一条示例行

**验收**：现有 13 行改用推导预算后，与手填值的偏差逐行可解释；恒真/不可满足表达式被拒；存量对局结果不因预算口径变化而意外翻转。

### P2 · 数值表达式

已定 A 档（§3.6）。施工步骤见 `docs/地基计划_虚拟原子与数值A.md` 的 G1。

**验收**：`grep -c BurstDamage` 降到只剩枚举与表行；三个参照族特例被"通用原子 + 参照 + 值引用"完全吸收；`RefAtomSingleTargetVerifier` 四场景断言一条不改、全 PASS。

## 7. 风险登记

| 风险 | 说明 | 缓解 |
|---|---|---|
| 概率表漂移 | 新真相源，随卡池/平衡变化 | 版本戳 + 大版本重测 + 缺失即拒绝 |
| 区间过宽 | 嵌套 `&` 会把 `[lo,hi]` 撑到近全区间，预算压到 1 档 | 报错引导作者拆分；深度/token 上限 |
| 概率表进不了摘要 | 合法性变化不换号，两端静默分歧 | 概率表版本纳入握手（§2.8） |
| 文本泄漏进身份 | 改格式换号 | 规范化 AST 哈希（§4.2） |
| 数值表达式侵蚀定价 | 从"取值引用"滑到"完整表达式" | 分档推进；C 档明确不做 |
| 作者用恒真条件白嫖 | `A \| !A` 等于无条件奖励 | 校验第 5 条拦截 |

## 9. 一句话收口

**条件**：作者只写"条件是什么"，引擎算"条件值多少"——算的依据是现有 13 行手填值所蕴含的那条 `1/P` 曲线。

**数值**：不按上界定价，按名义值定价；表达式只取值、不运算，先把三个特例原子吃掉。

**共同**：都在装载边界编译完，结算期引擎不再认识"玩家"这个词。
