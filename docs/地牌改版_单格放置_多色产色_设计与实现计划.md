## 1. 已定稿决策（2026-11-15 用户拍板）

| # | 问题 | 决策 |
|---|---|---|
| 1 | 多色卡一次横置产几个元素 | **1 个**。颜色从该卡“可产集合”中选一个；不是一次产所有色。 |
| 2 | 自动/手动的关系 | **自动付费默认一直开启**，不设全局“自动/手动”开关。手动 = 玩家主动点地牌预生成临时元素；多色地此时弹**已有选色弹窗**（Region 列表）选一个色。 |
| 3 | 多色地算不算多色（按色地牌数） | **算**。一块地只要“可产该色”，就计入该色的地牌数（禁召令/归土/纳川/代价地牌门槛/单色可用性等）。 |

> 术语纠偏：本改版后“自动/手动”不是两个规则档位，而是**两套产色入口**——
> 自动 = 付费时系统按账单规划横置；手动 = 玩家先点地牌把元素预生成到临时钱包。
> 两者共用同一套支付规划，自动始终可用。

## 2. 一句话结论

这不是“把放地选色弹窗删掉”的小改动。`LockedColor` 是地牌资源模型的单点：
全仓 **74 处引用 / 27 个文件**，支付规划、按色地牌计数、快照/联机、回放、AI 观测与动作空间都挂在它上面。
真正的改造点是：

1. **数据模型**：`PooledCard` 从“单锁色”改成“可产集合 + 展示色”；
2. **支付规划**：从“按单色分桶 + 同色钱包优先”改成“钱包全链优先 + 地→色匹配”；
3. **按色计数**：所有 `LockedColor == color` 改成 `CanProduce(color)`；
4. **表现/联机/AI/夹具**：把“锁色”降级为“展示色”，并逐处改口径。

第 1 条决策（一次 1 个元素）保证了地牌资源曲线不变；第 3 条决策是**平衡改动**，不是纯重构，需要按改动后的强度重新评估禁召/归土/纳川/代价门槛。

## 4. 目标规则（正式口径）

### 4.1 放置

- 手牌拖到己方地牌区（`land-strip-*` / `land-quad-*` / 地牌行 tile），满足以下条件即算放置：
  - `CanServeAsLand(card)`（正式生物/法术/结界；非衍生物/临时复制卡）；
  - 己方地牌槽未满（`CanAddLand`）；
  - 己方主阶段；无禁地令；教学引导放行；
  - 该卡有可产色（`GetLandColorChoices` 非空；0 费/纯黑白不可作地牌）。
- **不再让玩家选色**；入池时记录：
  - `ColorOptions` = 放置瞬间的 `GetLandColorChoices(card)`（**快照**，不随之后的费用增减/锚价变化实时推导）；
  - `DisplayColor` = `ColorOptions[0]`（份额最多色，仅展示/落格/日志用，**不限制产色**）。
- 拒绝文案把“无可锁定产色”改成“该卡无元素费用，不能作为地牌”。

### 4.2 产色

- 一次横置 = 产 **1 个**元素，颜色 ∈ `ColorOptions`；地牌随即横置，本回合周期不再产。
- 自动：付费规划按账单选色（§5），玩家不选。
- 手动：玩家点地牌；单色直接产，多色弹窗选一个色（§7）。
- 产物落临时钱包，任一回合结束清空。
- 事件 `ElementPoolGainEvent.GainedType` = 本次实际产出色；`ElementPoolAddEvent` 继续携带 `LockedColor`（语义改为“展示色”），可产集合由卡数据/`PooledCard.ColorOptions` 推导。

### 4.3 按色计数

- “某色地牌数”= 元素池内 `CanProduce(color)` 的地牌数；横置与否按各调用点原口径，**只换颜色谓词，不动横置口径**。
- 多色地同时计入多个颜色；双色地一块顶两块（决策 3，平衡改动）。
- 展示格（`DisplayColor` 对应的 4 格之一）只是棋盘锚点，不参与“某色地牌数”判定。

### 4.4 临时钱包

- 单池 `TempElements`；手动/效果来源不区分。
- 付费时钱包优先于地牌；“手动优先”= 先花掉已生成的临时元素，再横置新地牌。
- 回合结束双方钱包清空（现有 `OnTurnEnd` 不变）。

## 5. 支付规划（核心改造）

### 5.1 现状的两个问题

**问题 A：多色地不能按单色分桶。**
`PlanBill` 现在按 `land.LockedColor` 把未横置地牌塞进单色队列（[ElementPool.cs:490](../Assets/Scripts/HotUpdate/CardCore/BaseSystems/ElementPool.cs#L490)）。
如果一块红蓝双色地被同时放进红、蓝两个队列，账单“红1+蓝1”会被同一块地 `Taps.Add` 两次：支付成功，但只横置一次，等于凭空多产 1 点。
**一块地一回合最多贡献 1 点，且只能选一个色**，必须做“地→色”的匹配，不能简单并队列。

**问题 B：跨色链不是钱包优先。**
`PlanBill` 是“同货币内钱包优先”，不是“全链钱包优先”（[ElementPool.cs:515](../Assets/Scripts/HotUpdate/CardCore/BaseSystems/ElementPool.cs#L515)）。反例：

> 账单 1 灰；钱包 1 红（手动横置产）；场上有 1 灰地 + 1 红地。
> 灰链 = [灰, 红, 蓝, 绿, 彩]：先看灰货币，钱包 0 → **直接横置灰地**；
> 红钱包要等灰地队列耗尽才轮到。结果：横置了不想横的灰地，红临时元素留到回合末清空。

这正是“玩家横置了自己不想横置的卡”。决策 4 要求“钱包优先”，所以必须把钱包的消耗提到所有地牌横置之前。

### 5.2 推荐算法：最小费用流（小图，确定性）

把账单拆成“需求单位”，把钱包和未横置地牌作为供给，做一次二部匹配/最小费用流：

```
源点 S
  ├─ 钱包货币节点 W_c       容量 = wallet[c]，费用 0
  └─ 地牌节点 L_i           容量 = 1（每块地只能横一次）
货币节点 C_c（地牌实际产出的货币，用于恢复 TapColor）
需求节点 N_d（d=红/蓝/绿/灰/…）容量 = bill[d]
汇点 T

边：
  W_c → N_d   若 c ∈ ChainFor(d)，费用 = 该货币在链中的序号（0=本色，越大越靠后）
  L_i → C_c   若 c ∈ L_i.ColorOptions，容量 1，费用 = BIG（一次横置）
  C_c → N_d   若 c ∈ ChainFor(d)，费用 0
  N_d → T     容量 bill[d]，费用 0
```

求最小费用最大流：
- 最大流 < 总需求 → 不可付（返回 null，不改状态）；
- 否则总费用 = `BIG × 横置张数 + 钱包链序罚分`。`BIG` 取远大于“账单总点数 × 最大链序罚分”的值（例如 10000），保证**横置张数最少**优先，钱包链序只在同横置张数时做平局；
- 天然满足：
  1. **先尽量用钱包**（横置费用 BIG 远大于钱包罚分）；
  2. 同色钱包优先于 Any（链序罚分）；
  3. 横置张数最少；
  4. 每块地最多用一次，多色地只会被分配一个色；
  5. 地牌经 `C_c` 节点可以恢复“本次产出色”，直接写进 `TapColor`/`PaidCost`。
- 确定性：节点/边按固定序建（钱包按 ManaType 序、地牌按池序、需求按 `FourColorOrder`），最短路平局按节点索引打破。回放/AI 对拍要求同一状态两次规划结果逐项相同。

> 规模：钱包 5 色 + 地牌 ≤ 40 + 需求 ≤ 5，边 < 200，流量 ≤ 账单总点数；`CanAfford` 每帧调用也足够。
> 可加单色快速路径（只有一种需求色时直接算），但正确性以流为准。
> 实现量约 100~150 行（SPFA/Bellman-Ford 增广即可，不需要外部库）。若评审认为过重，可退化为“钱包全链优先 + 地牌匹配 + 失败回溯”，但必须逐条通过 §5.4 用例。

### 5.3 执行

- `PlanBill` 返回：
  - `WalletUse`：各货币扣多少；
  - `Taps`：横置哪些地牌，以及每块地本次产出色（新增 `TapColor`，供事件/台账）；
  - `TotalPaid`：按**货币**计的实际支付组合（钱包 + 横置合计，保持现有 `PaidCost` 口径）。
- `TryPayBillWithAutoTap` 先规划后执行：扣钱包、置 `IsTapped`、发 `ElementPoolPayEvent`；失败不动任何状态。
- `CanPayCostWithAutoTap` 走同一规划器；**预检与结算必须同源**，不能一个用旧分桶、一个用新匹配。
- `cap`（浓度上限）在“1 地 1 元素”模型下天然有界（横置数 ≤ 池张数 ≤ cap），规划器可不再使用 `cap` 参数；保留参数时只作断言/防御。

### 5.4 关键用例（必须写成测试）

| 用例 | 期望 |
|---|---|
| 账单灰1；钱包红1；灰地+红地 | 花红钱包，**不横置**（修复问题 B） |
| 账单红1；钱包彩1；红地 | 花彩钱包，不横置（钱包优先于地牌） |
| 账单红1+蓝1；场上仅 1 块红蓝双色地 | **不可付**（一块地一回合只能产 1 点） |
| 账单红1+蓝1；2 块红蓝双色地 | 可付，各横 1 块，一块产红一块产蓝 |
| 账单红1+蓝1；1 块红蓝双色地 + 钱包红1 | 可付：钱包红付红，双色地产蓝 |
| 账单红1+灰1；红地+灰地；钱包 0 | 可付：红地产红、灰地产灰（灰地不能产红；红地虽可垫灰，但红需求只有它能付） |

### 5.5 已知风险：pending 声明承诺

`CanAffordCast` 会把同玩家已声明未结算的费用合并成一张账单做预检（[GameActions.Costs.cs:168](../Assets/Scripts/HotUpdate/CardCore/GameCore/GameActions.Costs.cs#L168)），但实际结算是逐张卡分别调用 `TryPayBillWithAutoTap`。
合并预检能保证“总资源够”，但不能保证“逐张结算顺序”下每张都够：例如两张 pending 都只能靠同一块地，合并账单里这块地只能用一次 → 预检会拒；但若两张各有多条路径，逐张贪心可能先占掉后一张唯一的路。
单色地时代这个问题就存在，多色地会让可选路径更多、更容易掩盖。建议：
- 短期：加“pending 双卡共用一块地/两块地”的回归用例，确认逐张结算不会失败；
- 长期：pending 支付保留一份全局分配（或结算时带 lookahead 重规划）。

### 6.2 可产集合的范围

`GetLandColorChoices` = 卡面/各模式推导费 **∪ 全部主动效果锚价** 的红/蓝/绿/灰，按份额降序（[ElementPool.cs:175](../Assets/Scripts/HotUpdate/CardCore/BaseSystems/ElementPool.cs#L175)）。

决策 3 的“算”默认按这个集合算，即：
- 一张红费卡如果主动效果锚价是蓝，它可以产蓝，也**同时计入蓝地数**；
- 一张灰+绿卡同时计入灰地和绿地；
- 四色测试卡“试作·元素井”同时计入四色。

这比“印刷双色”更宽。如果只想按印刷/推导费算、不让主动效果锚价参与计数，需要单独划线（见 §15 待定项）。**推荐默认用同一集合**，否则会出现“能产蓝但不算蓝地”的口径分裂。

### 6.3 连带影响

- `GetRemainingElementTotal`（[ElementPool.cs:629](../Assets/Scripts/HotUpdate/CardCore/BaseSystems/ElementPool.cs#L629)）仍按“未横置地牌 ×1”算，决策 1 下正确，无需改。
- `CostRejectText` 的“总费 > 地牌槽上限”提示仍成立（1 地 1 元素）；但错误文案里的“锁色”要改。
- 决策 3 会让禁召/归土/纳川/代价门槛明显变强；这不是 bug，是平衡改动，需按 §12 重测。

## 7. 手动产色（决策 2）

### 7.1 交互流程

1. 玩家点己方未横置地牌面片（`land-quad-*`）或 Information 窗【生成】。
2. 时点闸（`GateTapLand`）：己方主阶段 ∨ 持有优先权；教学/联机按现状拒绝（教学见 §7.4，联机见 §9）。
3. 取该地牌 `ColorOptions`：
   - 只有 1 个色 → 直接 `TapLandForElement(core, player, card, color)`；
   - 多个色 → 弹**已有选色弹窗**（`PickRegionOptionAsync("选择地牌产色", …)`，选项如“生成 红 / 蓝 元素”，顺序=可产集合序，主色在前）；取消=不横置、不产色。
4. 成功：地牌横置、临时钱包该色 +1、toast“已横置 X：生成 1 个Y元素”；对账面片/饼图。

> 弹窗期间按现有 Region 选择态处理（3D 点击让路，避免误点第二块地）；取消=不横置、不产色。
> 选项顺序=可产集合序（主色在前），不做默认高亮，防手滑选错色。

### 7.2 引擎接口

```csharp
// 建议签名（示意）
public static bool TapLandForElement(GameCore core, Player player, Card landCard,
    ManaType color, out string reason);
```

- 校验：在池、未横置、未冻结、时点闸、`color ∈ pc.ColorOptions`；
- 产 `TempElements[color] += 1`，发 `ElementPoolGainEvent { GainedType = color }`；
- 不改变 `TapsThisTurn` 的“付费自动横置次数”口径（手动仍不计）。

带“地牌特性”的生物 `TapCreatureForElement` 目前取费用首个色（[GameActions.cs:113](../Assets/Scripts/HotUpdate/CardCore/GameCore/GameActions.cs#L113)）。建议与地牌同口径（多色时弹窗/自动选），否则两套产色规则；若暂不改，需在文档/悬停里写明“生物产色仍取首色”。

### 7.3 “避免横置不想横置的卡”怎么落地

- 自动始终开启，所以玩家不能“阻止自动横置”所有地牌；能做的是**先手动把需要的元素产出来**，支付规划钱包优先，自动只会横置剩余缺口。
- 因此 §5.1 问题 B 是这一体验的硬前提：如果灰需求先横灰地、红钱包留到回合末，手动预生成就白做了。
- 手动产出的元素与效果产出的同色元素同池，支付时都会先于地牌被消耗；不需要来源标记（决策 4）。
- 若玩家手动产多了，未用完的元素在回合结束清空——这是现有规则，不是新问题。

### 7.4 教学/联机

- 教学：`GateTapLand` 现在一律拒绝手动产色（[BattleScreen.Board.cs:730](../Assets/Scripts/HotUpdate/UI/Screens/BattleScreen.Board.cs#L730)）。若教学要教“手动产色”，需要接 `RuleHooks.TutorialTapGate`（目前只赋值、无调用点）并加教学步骤；否则保持拒绝。
- 联机：现在 toast 拒绝手动产色；自动付费仍可用。多色卡在联机暂时没有“手动指定色”的入口（见 §9）。
- Information【生成】按钮：与面片点击是同一终态；建议**退役/隐藏**，只保留面片点击一条主路径，避免两条入口的选色体验不一致。若保留，必须走同一多色弹窗。

## 12. 平衡影响

### 12.1 量级

- 现有池 215 张卡中，**42 张有两色以上费用（含灰）**，其中**非灰双色只有 4 张**（`TutorialCards` 28/150，`TrainingCards` 14/65）。
- 所以“多色”如果含灰，接近 **20%** 的卡会从“灰/本色二选一锁色”变成“灰/本色双模地”；如果只算非灰双色，目前影响很小。
- `GetLandColorChoices` 还包含主动效果锚价，实际可产集合可能比印刷费用更宽；这会让“可产即算”的计数进一步放大。

### 12.2 决策 3 的具体 Buff

- 禁召令：红地数/绿地数决定可放生物的攻击/生命；一块红绿地同时顶红、顶绿。
- 归土：绿地数决定墓地复活费用上限；绿双色地直接抬高上限。
- 纳川：蓝地数抬手牌上限；蓝双色地直接加手牌上限。
- 代价地牌门槛：按色地牌数满足代价生成面；双色地一块满足两个色。
- 单色可用性条件（`SpecificManaTypeAvailable`）：未横置的多色地同时满足多个颜色条件。
- 测试卡“试作·元素井”四色，若进入正常池会同时顶四色；目前仅测试用，需确认不会被正常卡组引用。

### 12.3 决策 1 的保护

- 一次横置只产 1 个，`GetLandCap`/`GetRemainingElementTotal`/费用上限闸的资源曲线不变；
- 不会出现“双色地一块付两点”的爆炸；`PlanBill` 的每地 1 点容量是硬约束。

### 12.4 建议的平衡测试局

- 禁召令 + 红绿双色地：确认攻击/生命阈值是否过强；
- 归土 + 绿双色地：复活费用上限是否跳得太快；
- 纳川 + 蓝双色地：手牌上限增长是否超预期；
- 代价门槛 + 双色地：高代价卡是否变得太容易发动；
- 灰+色双模地（20% 卡）在铺地/付费中的实际灵活性；
- 四色测试卡只在测试局出现，确认不进入玩家卡池/预组。

## 14. 风险与回滚

| 风险 | 处置 |
|---|---|
| 支付规划改错 → 预检能付、结算付不出 | `CanPay`/`Pay` 共用同一 PlanBill；加“预检=true 必成功”的属性测试；失败不动状态 |
| 同一块多色地被规划两次 | 流网络里地牌节点容量=1；加“1 块双色地付红1+蓝1 必失败”用例 |
| 规划不确定 → 回放/AI 对拍漂移 | 固定节点/边序 + 平局规则；同状态两次规划逐项相等 |
| pending 多卡共用资源 | 加双 pending 用例；必要时保留全局分配/结算重规划 |
| 旧存档/旧回放不兼容 | `LockedColor` 字段保留为展示色；缺集合时用卡数据兜底；协议暂不新增字段 |
| 联机本地/服务端口径分裂 | 服务端同用新规划器；先做放置 `-1` + 自动支付，再评估手动 intent |
| AI 旧模型失效 | 动作/观测 schema 版本化；先保留展示格，再加可产掩码；重训后再切换 |
| 教学/测试夹具失真 | 保留 forced 色重载；40 张素材地与 `tokenType` 逐场对拍 |
| 面片拖拽命中不到 | 视觉块与 `land-strip-*` collider 对齐验证；落在块上必须判 Land，不能判 Field |
| 平衡超预期（禁召/归土/纳川/代价门槛变强） | 按 §12.4 重测；必要时只对“计数”收紧到印刷费用色（见 §15） |
