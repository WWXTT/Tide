## 1. 背景：为什么现在的联机日志必然漂

### 1.1 现状链路

```
引擎事件 (IGameEvent, 全信息, 服务器本地)
   ├─ MatchLogService.Appended ──► 本地局: MatchLogRenderer 渲染 ──► BattleLogController（木桩口径，全量可读）
   └─ NetEventProjector（反射公共属性 → NetEvent）──► 按座位过滤 ──► 线上 116 NetEventBatch
                                                          └─► 客户端: NetLogRenderer 再渲染一遍（降级口径）
```

联机局的战报**不是**"日志"下发的，而是"事件投影"的副产品：客户端拿着被投影裁剪过的事件，用**第二套映射**（`NetLogRenderer`，460 行）去猜木桩会怎么说。投影面 ≠ 领域对象面，于是必然有行出不来。

### 1.2 实测成本（无头 AI 整局，`MemoryPack` 真实序列化字节，seat0 视角）

| 口径 | 短局（5–7 回合 / 约 790 事件） | 长局（35–38 回合 / 约 2700 事件） |
|---|---|---|
| **A 现行全量事件流** | **162.1 KB/局** | **574.4 KB/局** |
| B 只发"会出行"的事件 | 57.8 KB | 185.4 KB |
| C 全量但去掉每参数 `FieldName` | 133.1 KB | 473.4 KB |
| D 有行事件 + 去字段名 | 47.3 KB | 151.8 KB |
| E 服务端渲染文本（UTF-8 + 1B 颜色） | 10.5 KB | 39.0 KB |
| **F 行流真实线上字节**（Kind+Flags+EventId+文本，64 行/批） | **13.7 KB/局** | **49.9 KB/局** |
| **F / A** | **8.5%** | **8.7%** |

- 每事件平均 **208 B**；每行平均 **63 B**。
- **69%～70% 的事件完全不产出行**（`PriorityPass` / `PriorityGain` / `CardZoneChange` / `StackEmpty` / `AtomicEffectPhase` / `StackResolutionEnd` 等），却照样付信封+字段名的钱。
- 反证：终局摘要（v11 `MsgMatchSummary.Log`）**已经**在每局末下发一份服务端渲染的完整战报 markdown（20–40 KB，`TagTable.MMS_Log`）。"服务器下发日志文本"这件事现在就在做，只是只在终局做了一次。

### 1.3 结论

**让服务器下发渲染好的战报行，比现在下发事件流便宜约 11 倍。** 矛盾不在"日志文本太贵"，而在"投影面撑不起木桩口径"。本方案把日志从"投影的副产品"提升为"服务端渲染的一等产物"，并顺带删掉第二套映射。

## 2. 目标与非目标

### 2.1 目标

1. **规格对齐**：联机战报逐行、逐字对齐木桩（`MatchLogRenderer` 的观侧口径），唯一例外是"必须遮蔽的隐藏信息"（见 §3.2）。
2. **成本下降**：单局日志下行 ≤ 现状 10%（实测 8.5%）。
3. **单一映射**：`NetLogRenderer` 退役；"事件→文案"只有 `MatchLogRenderer` 一份，两端编译同一份源码。
4. **行序单源**：建局静默、回合自然抽挂起、连锁开合、终局行——时序整理下沉到共享类，服务端产出的是"最终入史行"，客户端只 append。
5. **不引入新的人工维护面**：新增引擎事件时，只改 `MatchLogRenderer`（现状要求同时改投影或改 `NetLogRenderer`）。

### 2.2 非目标（本期不做）

- 不改本地局、教学、挑战的日志行为（重构后行为必须逐字不变）。
- 不改快照（`GameStateSync`）、intent、反问通道。
- 不做断线重连补发（现状断线即作废，本方案沿用）。
- 不做日志本地化（当前全库中文硬编码，文本在服务端生成；未来要本地化另立方案）。
- 不做观战/回放专用能力（观战沿用现有 `viewerSeat=-1` 全信息口径）。
- 不改 AI 填位客户端（`NetClientBrain`）的事件流消费——它保留事件流。

## 3. 目标规格

### 3.1 与木桩逐字一致的行

`MatchLogRenderer.Render(e, isSelf)` 的**全部**产出行（见其 case 表），联机与本地一字不差，包括：

| 行类别 | 示例 | Class |
|---|---|---|
| 回合骨架 | `—— 回合 7：对手 ——` | `log-line--turn` |
| 准备阶段账目 | `〔准备阶段〕我方重置：地牌 3 张解横置、技能就绪、地牌槽上限→5` | `log-line--phase` |
| 阶段 | `〔主要阶段〕` | `log-line--phase` |
| 抽牌（只报数量） | `对手 抽 2 张` | 默认 |
| 打出/入场/离场 | `我方 使用 锚点生物0`、`锚点生物0 入场（可用，来源 效果召唤）` | `log-line--card` |
| 区域移动 | `对手 弃置 X`、`X 洗入牌库` | `log-line--card` |
| 钱包（**含支付明细**） | `我方 支付 红×2 蓝×1（打出：X）` | 默认 |
| 战斗 | `〔攻击〕… → …`、`… 死亡（伤害致死）` | `log-line--combat` |
| 连锁叙事 | `我方 被询问是否连锁`、`连锁开始逆处理：【X】`、`连锁结束` | `log-line--system` |
| 效果发动/结算 | `我方 发动：X「效果名」`、`　→ 效果名（数值）` | `log-line--effect` |
| 关键词白名单 | 守护/运势/耐久（`CounterRules` 文案） | `log-line--effect` |
| 指示物 | `X 获得 2 层攻击力增加（攻击 2→4）` | `log-line--effect` |
| 技能 | `〔技能〕我方 发动英雄技能「X」` | `log-line--effect` |
| 终局 | `★ 我方获胜（生命归零）· 共 22 回合` | `log-line--system` |

这些行现在在联机里缺的（`HeroSkillActivatedEvent` 字段不可投影、`TurnEndCounterSummaryEvent.Parts` 字段不可投影、`PaidCost` Opaque、`StackAdd.AddedObject` Opaque、`EffectExecutionSummary.Description` 线上剔除）**全部由服务端渲染解决**，不需要动协议投影规则。

### 3.2 与木桩**刻意**不同的行（遮蔽规则）

木桩局对手是 AI，日志会写出对手手牌/牌库里的卡名。联机不能照抄。规格定义为**三条遮蔽规则**，由服务端按接收者视角执行：

| # | 场景 | 木桩输出 | 联机输出 |
|---|---|---|---|
| R1 | `CardEnterHandEvent`：接收方是**对手**、`FromZone ∈ {Deck, None}`、且该卡未被展示（`RevealRules.IsExposed`=false） | `对手 获得 X（来自 牌库）` | `对手 获得 未知卡（来自 牌库）` |
| R2 | `EffectExecutionSummaryEvent.Description`（服务器拼装文本，可能内嵌隐藏卡名/实掷数值） | `　→ 在我方场上召唤 2 个…（完整描述）` | `　→ 效果名`（走 `EffectsLibrary` 短名，不上描述文本） |
| R3 | `GameStartEvent` 开局块（双方牌库/起手清单） | 受 `AllowHiddenInfo` 闸，真实对局已退化为"谁先手" | 同左；且该块在首个回合行前，已被"建局静默"丢弃 |

其余所有卡名都来自**公开区**（战场/墓地/除外/元素池/发动区/额外区）或**已展示**（`RevealRules.IsExposed`）的卡，允许原名——这与规则本身一致，不算泄露。牌库顶磨入墓地（`CardMillEvent`）也是公开的（墓地是公开区）。

> **验收口径**：R1/R2 之外，联机行文本必须与"同种子本地局 seat0 视角渲染"逐行相等。

### 3.3 可见性判定时点

在**事件发布时**判定（`MatchLogService.Appended` 回调内），而不是出队时。理由：渲染需要活体对象（延迟到出队时，死亡/移区后 `GetZone()` 已变，`MatchLogRenderer.DestroyLine` 的注释就是这个坑）。R1 是纯规则判定（区域+归属），不依赖实时状态，更稳。

## 4. 架构

### 4.1 目标数据流

```
引擎事件 (IGameEvent)
   │
   ├─ MatchLogService.Appended ──► MatchLogLineStream[seat0]  ─┐
   │                          ──► MatchLogLineStream[seat1]  ─┼─► 行队列（每座位一条，带 base 游标）
   │                          ──► MatchLogLineStream[-1 观战]─┘        │
   │                                                                   ▼
   │                                                     NetRoom.FlushDownlink（每 tick）
   │                                                          按成员 LogCursor 切片，64 行/批
   │                                                                   │
   │                                                         135 NetLogBatch（MsgNetLogBatch）
   │                                                                   ▼
   │                                                     NetGameClient.OnLogBatch
   │                                                                   ▼
   │                                                     BattleLogController.AppendServerLine
   │
   └─ NetEventProjector ──► 116 NetEventBatch ──► 仅 AI 填位客户端消费（P3 起人类连接停发）
```

| 层 | 负责 | 不负责 |
|---|---|---|

## 5. 详细设计

### 5.1 新增 `MatchLogLineStream`（时序整理单源）

**位置**：`Assets/Scripts/HotUpdate/CardCore/Effects/MatchLogLineStream.cs`（与 `MatchLogRenderer` 同目录，服务器共享源通配已覆盖）。

**为什么必须下沉**：现状 `BattleLogController.ProcessEntry` 里的三条时序规则（`_logArmed` 建局静默、`_standbyDeferred` 自然抽挂起、`PhaseStartEvent` 放行）是"行序"的唯一实现。服务端要产出同样的行序，就必须用同一份代码，否则行序会二次分叉。

```csharp
namespace CardCore
{
    /// <summary>最终入史行（服务端下发 / 本地 UI 共用）。</summary>
    public struct MatchLogLine
    {
        public string Text;
        public string Class;     // log-line--*
        public byte Kind;        // Class 的线上编码（1..6，见 MatchLogLineKind）
        public byte Flags;       // MatchLogLineFlags
        public uint EventId;     // 去重/对拍锚
    }

    public enum MatchLogLineKind : byte
    {
        Default = 0, Turn = 1, Phase = 2, Combat = 3, Effect = 4, Card = 5, System = 6,
    }

    [System.Flags]
    public enum MatchLogLineFlags : byte
    {
        None = 0,
        FirstDraw = 1,   // 回合自然抽（已排序放行，仅供调试/对拍）
        TurnStart = 2,   // 回合骨架行
        ChainStart = 4,  // 真连锁开始逆处理（RealCount≥2）——客户端自动展开日志面板
        ChainEnd = 8,    // 连锁结束（HadRealItems && WasChain）——客户端自动收起
        GameOver = 16,   // ★ 终局行——客户端据此收口对局 UI（替代事件流 GameOver 探测）
    }

    public sealed class MatchLogLineStream
    {
        /// <param name="isSelf">观侧判定（座位归属）。观战流传 null ⇒ 中立实名口径。</param>
        /// <param name="redactEffectSummary">R2：效果摘要只出短名、不出 Description（联机=true，本地=false）。</param>
        public MatchLogLineStream(System.Func<Player, bool> isSelf, bool redactEffectSummary);

        /// <summary>喂一条事件，产出的行追加到 sink（0..n 行）。</summary>
        public void Append(IGameEvent e, System.Collections.Generic.List<MatchLogLine> sink);

        /// <summary>兜底放行挂起的回合自然抽（下回合头行前 / 对局结束 / 退屏）。</summary>
        public void Flush(System.Collections.Generic.List<MatchLogLine> sink);

        /// <summary>跨局复位（armed/挂起清空）。</summary>
        public void Reset();
    }
}
```

**内部状态机**（从 `BattleLogController.ProcessEntry` 平移，行为必须逐字等价）：

```
Append(e):
  if e is TurnStartEvent:  armed = true; Flush(挂起的自然抽)
  if (!armed) return                        // 建局事件（起手抽/护甲注入）不入史
  line = MatchLogRenderer.Render(e, isSelf, redactEffectSummary)
  if line empty: return
  if e is CardDrawEvent && FirstDrawOfTurn: 挂起；return
  sink.Add(line + flags)
  if e is PhaseStartEvent: Flush(挂起的自然抽)   // 〔准备阶段〕行落定后放行
```

**Flags 判定**（与 `BattleLogController.AutoToggleForChain` / `NetAppendLog` 同判据，收敛到一处）：

- `ChainStart`：`StackResolutionStartEvent s && s.TopItem != null && !s.TopItem.IsPhaseWindow && s.RealCount >= 2`
- `ChainEnd`：`StackEmptyEvent se && se.HadRealItems && se.WasChain`
- `GameOver`：`GameOverEvent`
- `TurnStart`：`TurnStartEvent`

### 5.2 渲染可见性（`MatchLogRenderer` 扩展）

```csharp
public static Line Render(IGameEvent e, Func<Player,bool> isSelf,
                          bool redactEffectSummary = false)
```

- 只加一个 `redactEffectSummary` 开关（默认 `false` ⇒ **本地局 / 导出 / 调试口径零变化**）。
- **不加"通用可见性谓词"**：遮蔽只有 R1、R2 两个渲染点，按规则判，不按"隐藏集快照"判（快照口径会把"刚公开/刚展示"的卡误遮）。

```csharp
case CardEnterHandEvent hand:
    if (hand.IsDraw) return Empty;
    // R1：对手从隐藏区入手、且该卡未被展示 → 卡名遮蔽
    bool fromHidden = hand.FromZone == Zone.Deck || hand.FromZone == Zone.None;
    if (fromHidden && isSelf != null && !isSelf(hand.Player) && !RevealRules.IsExposed(hand.Card))
        return new Line($"{Who(hand.Player, isSelf)} 获得 未知卡（来自 {ZoneZh(hand.FromZone)}）", "log-line--effect");
    return new Line($"{Who(hand.Player, isSelf)} 获得 {Name(hand.Card)}（来自 {ZoneZh(hand.FromZone)}）", "log-line--effect");
```

- `isSelf == null`（导出/中立口径）⇒ R1 不生效（与 `AllowHiddenInfo` 同为"调试口径"闸）。
- `redactEffectSummary == true` ⇒ `EffectExecutionSummaryEvent` 出 `"　→ " + EffectShortName(EffectId)`（R2），不出 `Description`。短名是公开信息（效果挂在公开卡上），描述文本才可能内嵌隐藏卡名/实掷数值。
- `EffectShortName` 从 `BattleView.EffectShortName`（UI 层）下沉到 `MatchLogRenderer`（CardCore，服务端可用；底层 `EffectsLibrary` 本就在 CardCore），`BattleView` 改为转发——仍是单源。

**服务端构造**（`NetRoom.InstallLogStreams`）：

```csharp
// 每座位一条流：seats 0/1 观侧口径；观战 -1 用中立实名口径（isSelf=null）
new MatchLogLineStream(
    isSelf: seat < 0 ? (Func<Player,bool>)null : p => NetEntityMapper.SeatOf(p) == seat, // 引擎座位，非椅位
    redactEffectSummary: true);
```

### 5.4 服务端下发（`NetRoom`）

#### 5.4.1 订阅时序红线

`MatchLogLineStream` 必须在 `core.InitGame(...)` **之前**挂到 `MatchLogService.Appended` 上。

原因：`InitGame` 内部会 `Reset()`（清 `MatchLogService` 缓冲）并紧接着 `StartGame()` 发布**第一发 `TurnStartEvent`**。若在 `InitGame` 之后订阅，会漏掉它 ⇒ `armed` 永远为 false ⇒ 整局零行。

```csharp
// NetRoom.StartMatch，紧接 core.InitGame(...) 之前：
InstallLogStreams(core);

private void InstallLogStreams(GameCore core)
{
    _logStreams.Clear(); _logHistory.Clear();
    foreach (int seat in new[] { 0, 1, -1 })
    {
        _logStreams[seat]  = new MatchLogLineStream(
            isSelf: seat < 0 ? null : (Func<Player,bool>)(p => NetEntityMapper.SeatOf(p) == seat),
            redactEffectSummary: true);
        _logHistory[seat] = new List<MatchLogLine>(1024);
    }
    _onLogAppended = entry => { foreach (var kv in _logStreams) kv.Value.Append(entry.Event, _logHistory[kv.Key]); };
    MatchLogService.Appended += _onLogAppended;
}
```

> `seat=-1`（观战）：`isSelf=null` ⇒ 中立实名口径、R1 不生效（全信息），与观战快照口径一致。
>
> 线程：`MatchLogService.Appended` 在引擎发布线程同步触发；P2P 房主与 `TideServer` 都在逻辑线程跑引擎，与 `FlushDownlink` 同线程，无锁需求（沿用 `NetEventProjector` 的既有线程纪律）。

#### 5.4.2 下发

在 `FlushDownlink` 的事件流段之后加一段（顺序：RoomState → 事件流 → **行流** → 快照）：

```csharp
// ---- 战报行流：每座位一条历史，成员按 LogCursor 切片（观战取得 -1 流）----
foreach (var member in AllMembers())
{
    var history = _logHistory[member.MatchSeat == -1 ? -1 : member.MatchSeat];
    int total = history.Count;
    if (member.LogCursor >= total) continue;
    for (int offset = member.LogCursor; offset < total; offset += 64)
    {
        var chunk = new NetLogLine[Math.Min(64, total - offset)];
        for (int i = 0; i < chunk.Length; i++) chunk[i] = ToDto(history[offset + i]);
        member.SendPayload(NetworkMessageType.NetLogBatch, new MsgNetLogBatch { Lines = chunk });
    }
    member.LogCursor = total;
}
```

- `INetChannel` 新增 `int LogCursor { get; set; }`；`StartMatch` 里与 `EventCursor` 同点复位（座位/观战都是 `0`）。
- 历史容量：单局 ≤ 4096 行（实测长局 ~800 行），超长局按 1024 行截头并保留 `_logBase[seat]` 偏移（与 `NetEventProjector.MaxEvents` 同款防御）。
- 清理：在 `TeardownMatch()`（幂等，`Stop` 也走它）里 `MatchLogService.Appended -= _onLogAppended; _logStreams.Clear(); _logHistory.Clear();`——漏掉会导致跨局串行（下一局开局前的清零事件被旧流吃掉）。

#### 5.4.3 人类连接停发事件流（P3）

`INetChannel` 新增 `bool WantsEvents { get; set; }`：

- `IsAi == true`（AI 填位 `NetClientBrain`）⇒ `true`（它要事件做观察）。
- 人类座位 / 观战 ⇒ `false`：`FlushDownlink` 跳过 `NetEventBatch` 段。

> 依据：客户端 `NetEventBatch` 的唯一消费者是 `BattleScreen.Net.cs` 的 `NetOnEvents`（日志 + `GameOverEvent` 收口），P3 后两者都由行流承载。AI/验证器路径不变（V1/V6/V7 仍走事件流）。

#### 5.4.4 服务端额外成本

每事件最多 3 次渲染（seat0/seat1/观战），实测 2700 事件量级：一次渲染 ≈ 微秒级，整局 +十几毫秒；内存 ≈ 800 行 × 3 流 × ~120 B ≈ 300 KB。可接受。

### 5.6 边界与失败模式

| 场景 | 行为 |
|---|---|
| 断线 | 沿用现状：作废并退出（不补发）。`LogCursor` 无重连语义。 |
| 观战中途加入 | 从 `LogCursor = history.Count`（当前点）开始，不补历史（与现有观战事件游标口径一致；记为已知限制）。 |

| 服务端渲染异常 | 单个事件渲染 try/catch 兜底：跳过该行并 `TideLog.Error`（不中断对局），与 `NetEventProjector.ErrorCount` 同风格。 |
