## 验收口径（写进代码，单一来源）

- 18 格 = 模型执色 × 对手主题 × 座位，逐格 Δ = 模型胜率 − 同格脚本基线。
- **达标（2026-11-24 DSH 修订；口径不变，判定改成区间）**：仍是「17 个常规格每格 Δ ≥ 0 + 这 17 格中位数 ≥ +15pp」，但：
  - 每格先看**点估计**；某格 95% 区间跨 0 时**先加测该格**（+200 局）再判，不直接算输。
  - 中位数 ≥ +15pp（中位数抽样误差 ≈1pp，这条本身不抖）。
  - **噪声账（别凭感觉）**：每格 200 局时胜率 1σ ≈ 3.5pp，Δ = 模型 − 基线两侧独立 ⇒ `σ_Δ ≈ 5pp`、**95% 区间 ≈ ±10pp**。
    于是：真实 Δ=+15pp 的格几乎必过（z=3）；真实 +10pp 每格有 2.3% 概率测出负值（17 格全过 ≈ 67%）；真实在 0 附近的格基本是抛硬币——那种格本来就该算“没做到”，不是判据的错。
  - 原文「|Δ| < 7pp 的骑线格加测」比噪声还细（区间是 ±10pp），改为「**区间跨 0 就加测**」；每次 +200 局/格，直到区间离开 0 或不跨 0。
- **饱和格**（基线 +15pp > 100%，目前只有绿镜先手 97.8%）：按不退步判，模型胜率 ≥ 基线 − 5pp；同样用区间判。
- **best 选点**：17 格里 **Δ 的最小 Wilson 下界**（不是最小点估计）。理由：每格 24 局时 `σ_Δ ≈ 14pp`，取最小点估计等于在 17 个噪声格里挑最幸运的那个；认证前的 best 只是候选。
- **训练内候选门（每格 24 局，432 局/次；原文“16 局”是 C3 落地前的旧值）**：常规格 Δ ≥ −5pp。此门**只用于选点与预警，不作达标依据**：`σ_Δ ≈ 14pp` 时 17 格全过的概率 ≈ `0.64^17 ≈ 5e-4`，「连中 3 次即停」几乎不会触发——要真提前停，得把训练内评估提到每格 ≥96 局，或只看总胜率趋势。
- **认证才是真门**：停训后 `best` 和 `last` 各跑 `eval_matrix.py`（每对 400 局 = 每格 200 局），按上面的判定逐格走；`last` 只报告、不作达标依据。
- **认证预算**：每个 checkpoint 3600 局 ≈ 8 小时（按 8 秒/局），best + last ≈ 16 小时，加测另计；必须算进阶段 B 的关键路径。

### A6 实现提示（2026-11-24 18:05 DSH 读码后补；派活时照这份改）

**① 改两处展开器，不要改 6 个调用点。**
行发射有 6 个调用点——`:363`（手牌 PlayCard）、`:694`（RespondPlay）、`:721`（**牌库顶虚拟手牌**，A7 刚修的那类）、`:782`（Activate/技能）、`:949`（HeroSkill）、`:1058`（响应窗 PlayCard）——它们最终都落到 `AddRowsWithInteraction`（`:1583`）→ `ExpandCardTargets`（`:1125`）/ `ExpandPerAtomTargets`（`:1242`）。**只改这两个展开器**即可全覆盖。

**② 展开器里三类 spec 分开处理**（`:1253-1297`）：
- `PickOne`/`EffCount<=1`：已是「逐候选一行」，保持；
- 固定 k（`EmitCombinations`，`:1291`/`:1208`）：改「每步只出该 spec 的候选行（1 目标）」，闸累积、选满 k 自动提交；
- **可变数量**（`-1`/`-3`：`AddSubsetRows` `:1338`、`AddPrefixRows` `:1366`）：**必须多一条「提交当前选择」行**——否则模型没法表达“我就要 k 个”。建议每步行集 = 剩余候选（1 目标/行）+ 1 条提交行（`Targets`=已选集合、`[10]=0`、`[3]`=首个已选）；k≥1，选 0 个不提交；
- `AutoTake`（`:1276-1285`）：引擎自动取、不出行，但**提交行要保留它的原子序占位**。

**③ 顺序是最大的坑**：引擎预选队列按**原子序**消费 `Targets`。只要同一 spec 的挑选连续、按 `specs` 计划序（`:1246`）推进，提交行的 `Targets` 顺序就天然等于原笛卡尔积行序。
- `TargetSet.Counts`（动态数量）**必须由闸重建**（每个 dynamic spec 的已选数 → `atomIndex`），不能沿用旧的子集/全取逻辑；
- `ReferencePickOf`（`:1216`）取 `targets[0]`——提交行原样传即可，不必特殊处理。

**④ 闸（建议 `TargetPickGate`，仿 `HandLimitDiscardGate`）**
- 状态：`Active` / `CardId+EffectId+ModeIndex` / `SpecCursor` / `List<List<Entity>> Picked` / `NeedPerSpec`；
- `LAE` 每步查它：过滤已选目标、算剩余、决定出 pick 行还是提交行；
- `Step` 收到 pick 行：**不 Apply**，只入闸 + 返回新决策；收满或收到提交行才把累积集合塞回 `TideAction.Targets/Counts` 走原 Apply；
- **清理点一个都不能漏**：Apply 完成 / `Reset` / 回合结束 / 停靠开始与结束 / 异常兜底——漏一个就会把上一张卡的已选带到下一张。

**⑤ `[10]` 怎么出**：`TideAction` 加 `PicksRemaining`（默认 `Targets.Count`），`BuildFeatures` 写 `[10]=PicksRemaining`。否则 pick 行 `Targets.Count=1` 会让 `[10]` 恒为 1，模型看不出还剩几下。

**⑥ 驱动侧**：`TideHeadlessDriver.Step`（`:579`）里在 `_parkTcs != null` 分支（`:659`，响应窗停靠）之外加密「pick 行」分支——**两条路径都要**，否则响应窗里出多目标卡又退回一次性。
关键：pick 步**不能推进回合/相位**。别复用 `AdvanceToDecision`（`:827`，它会推进），新增 `RebuildDecision()`（等价一次 `Enumerate` + `BuildResult`）。

**⑦ 脚本/玩家路径不动**：`SimpleAI`（TideSim/AiDuelRunner）与人类 UI 都不走 LAE 行——这也是「同目标集同结算」对拍的根基。

**⑧ 验收顺序（照这个顺序验，别跳）**
