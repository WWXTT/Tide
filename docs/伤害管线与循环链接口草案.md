# 伤害管线与循环链接口草案（v0.1）

> 2026-11-09 草案。目标：把「单次伤害的分层」「伤害后的后果」「多个伤害事件之间的循环」拆成三层；让循环成为一等公民；让「报复 + 吸血」成为合法、可终止、可观赏的玩法；旧卡通过兼容层保持行为。
>
> 非目标：不改卡牌数据/目标选择/栈与回合/SBA 本体/UI 协议；不做全关键词全连通；不把卡牌逻辑 DSL 化。

## 0. 一句话

`ApplyDamage` 只做 facade；单事件走 `DamagePipeline`，后效走 `DamageAftermath`，多事件循环走 `DamageChain`。循环的收敛由 `ChainPolicy` + `LoopCost` + `SBA checkpoint` 承担，不再由 `ApplyDamage` 里的局部 guard 承担。

> **设计裁决（2026-11-09）**：报复 + 吸血是合法且玩家期望的组合，不做「禁止互弹」的全局规则。新卡默认 `UntilDeath + Life(1)`，让循环在有限步内以单死/双死收束；`OneBounce` 只作为旧卡兼容档，不是新卡的默认。
>
> 这意味着「稳定」不再靠把循环掐死在第一次反弹，而是靠**可见的血债**让它自然衰减。30 次闸/`MaxEvents` 只做断言，不做玩法。

## 1. 三层模型

```
ApplyDamage(request)
 ├─ DamageResolver.Resolve(request)
 │   ├─ DamagePipeline.Resolve(event)       // 100 Target .. 700 Apply
 │   └─ DamageAftermath.Process(result)     // 事件/吸血/荆棘/报复/病原体/剧毒
 └─ DamageChain.Pump()                      // 多事件调度 + SBA checkpoint + 收敛
```

| 层 | 负责 | 不负责 |
|---|---|---|
| `DamagePipeline` | 单次伤害事件的目标校验、替代、转移、增幅、防护、最终修改、扣血 | 不产生后续伤害、不决定死亡、不写触发队列 |
| `DamageAftermath` | 伤害落定后的事件、吸血/系命、荆棘/报复/病原体/剧毒的后续事件 | 不递归调用 `ApplyDamage`；只 `Enqueue` |
| `DamageChain` | 多事件排队、SBA checkpoint、`LoopPolicy`/`LoopCost`、`Visited`/`StateRepeat`、日志 | 不做伤害数学、不做单事件分层 |
| `ApplyDamage` | 兼容 facade：选 Resolver、调用、返回 `Dealt` | 不写规则、不写关键词分支 |

## 2. 单事件管线

### 2.1 层序（对外契约）

| Order | 层 | 职责 | 典型效果 | 铁律 |
|---:|---|---|---|---|
| 100 | `Target` | 校验目标存在/存活/合法；改目标后复检 | 目标失效、区域变化 | 只校验，不选目标；选目标归效果结算 |
| 200 | `Replace` | 改写数量/目标/类型/事件（替代） | 伤害封顶、伤害转为治疗、目标转嫁 | 每个替代件最多一次；深度上限；改目标后置 `TargetDirty` |
| 300 | `Redirect` | 转移承受者（守护/转移） | 守护改写、伤害转移 | 默认最多 1 跳；改目标后复检；默认不重跑 `Replace` |
| 400 | `Amplify` | 防护层**之前**的数量增幅 | 暴击、伤害翻倍、伤害 +N | 防护层看到的是增幅后的量 |
| 500 | `Prevent` | 圣盾/护甲/坚韧/免疫盾等吸收 | 圣盾挡一次、护甲逐点吸、坚韧 −1 | 全挡后 `Amount=0`；默认不进入 `FinalModify` |
| 600 | `FinalModify` | 防护层**之后**的剩余量修改 | 易损 +N、最低伤害、最终上限 | 默认只在 `Amount>0` 时执行；全挡不放大、不消耗 |
| 700 | `Apply` | 扣生命/耐久、生命锁、返回 `Dealt`/`Lethal` | 落血、耐久损失、生命下限 | 返回 `Lethal`，不直接决定死亡；死亡交给 SBA |

> 实现上 `Target` 是 `ITargetValidator`，不是注册进 `_stages` 的普通 Stage；`DamageStageOrder.Target` 只作为顺序常量/日志标签。`Resolve` 在入口和每次 `TargetDirty` 后调用它。

### 2.2 不变量

1. **每个效果必须声明 `Stage` + `Priority`**。禁止再出现「在 `ApplyDamage` 里第几段」这种物理顺序。
2. **`Replace`/`Redirect` 改 `Target` 后必须重新校验**。当前实现只在入口查一次存活/区域（见 `KeywordRules.ApplyDamage` 入口），替代改目标后没有复检。
3. **`Amplify` 在 `Prevent` 前，`FinalModify` 在 `Prevent` 后**。这是规则契约，不是实现细节：暴击让盾吸收翻倍后的量；易损只放大盾没挡住的部分。
4. **`Prevent` 全挡时 `FinalModify` 默认跳过**。与 2026-11-09 易损移位定案一致。
5. **`Apply` 不直接 `IsAlive=false`，但致死要锁存**。它返回 `Lethal=true`，目标标记 `PendingDeath`；SBA 前其他治疗可以改变生命数字，但 `PendingDeath` 实体不触发吸血/系命，且 `PendingDeath` 不能被清除。死亡/送墓/亡语仍由 SBA 决定。这样既保留 SBA 时点，又不会让吸血在 SBA 前把死者救活、破坏循环的势函数。
6. **任何 Stage 都不许递归调用 `ApplyDamage`**。后续伤害一律走 `FollowUpEvent` + `DamageChain`。
7. **`LifeLoss` 不进伤害管线**。生命流失不吃圣盾/护甲/坚韧，不触发吸血/系命/报复/荆棘；只受生命锁/上限影响。

### 2.3 当前实现到新层的映射

| 当前 `KeywordRules.ApplyDamage` 段 | 新层 | 迁移备注 |
|---|---|---|
| 入口 `target.IsAlive` 校验 | `Target` | 增加替代/转移后的复检 |
| `ReplacementEngine.CheckReplacements` | `Replace` | 改目标后置 `TargetDirty` |
| `GuardianRules.FindGuardian` 改写 | `Redirect` | `guardRerouted` 改为 `RedirectPolicy.MaxDepth` |
| 无实体（Spellban）钳 1 | `Amplify` 或 `Replace` | 层归属待定：它现在是防护前 |
| `ProtectionRules.ModifyDamage`（延时保护） | `Prevent`/`Rewrite` | 与暴击的先后会改变取整结果，见 §2.4 |
| 暴击 `Crit` 翻倍 | `Amplify` | 防护前 |
| `ApplyPreventionLayers` | `Prevent` | 圣盾 → 护甲 → 坚韧 |
| 易损 `Vulnerable` 放大 | `FinalModify` | 防护后、全挡跳过 |
| 落血/耐久/生命锁/死亡标记 | `Apply` | 死亡标记移出，交给 SBA |
| `DamageEvent`/`CombatDamageEvent`/`LifeChangeEvent` | `Aftermath` | 事件发布 |
| 吸血/系命 | `Aftermath` | 只回伤害，不回 `LifeCost` |
| 荆棘 | `Aftermath` | 产生 `FollowUpEvent`（`Halve`） |
| 报复 | `Aftermath` | 产生 `FollowUpEvent`（`UntilDeath`） |
| 病原体/剧毒 | `Aftermath` | 加毒素/消灭 |

### 2.4 一个必须对拍的行为变化

当前「减半护盾」在暴击之前（`KeywordRules.cs` 的 `ProtectionRules.ModifyDamage` 早于 `Crit` 翻倍）：

```
3 点伤害 → ceil(3/2)=2 → 暴击翻倍 → 4
```

新层序 `Amplify` 在 `Prevent` 前：

```
3 点伤害 → 暴击翻倍 → 6 → 减半（ceil）→ 3
```

两者不同。迁移时要么接受新规则并逐条对拍，要么把「减半护盾」归到 `FinalModify`。**层序是规则，不是重构细节。**

### 3.1 上下文与管线

```csharp
public sealed class DamageContext
{
    public DamageRequest Request;
    public Entity Source;
    public Entity Target;
    public int Amount;
    public int Prevented;
    public int Dealt;
    public int ReplacementDepth;
    public int RedirectDepth;
    public bool TargetDirty;
    public bool Fizzled;
    public bool Lethal;
    public readonly List<FollowUpEvent> FollowUps = new();
    public readonly List<DamageLogEntry> Log = new();

    public DamageResult ToResult(int chainDepth)
    {
        var result = new DamageResult
        {
            Source = Source,
            FinalTarget = Target,
            Requested = Request.Amount,
            Dealt = Dealt,
            Prevented = Prevented,
            Lethal = Lethal,
            Fizzled = Fizzled,
            ChainDepth = chainDepth,
        };
        result.Log.AddRange(Log);
        result.FollowUps.AddRange(FollowUps);
        return result;
    }
}

public interface ITargetValidator
{
    bool IsValid(DamageContext ctx);
}

public interface IDamageStage
{
    int Order { get; }
    void Apply(DamageContext ctx);
}

public sealed class DamagePipeline
{
    private readonly List<IDamageStage> _stages = new();
    private readonly ITargetValidator _targetValidator;

    public DamagePipeline(ITargetValidator targetValidator)
    {
        _targetValidator = targetValidator;
    }

    public void Register(IDamageStage stage)
    {
        _stages.Add(stage);
        _stages.Sort((a, b) => a.Order.CompareTo(b.Order));
    }

    public DamageResult Resolve(DamageRequest request, int chainDepth = 0)
    {
        var ctx = new DamageContext
        {
            Request = request,
            Source = request.Source,
            Target = request.Target,
            Amount = request.Amount,
        };

        if (!_targetValidator.IsValid(ctx))
        {
            ctx.Fizzled = true;
            return ctx.ToResult(chainDepth);
        }

        foreach (var stage in _stages)
        {
            if (ctx.Fizzled) break;

            // Replace/Redirect 改性目标后，在下一层前复检；
            // 不重跑 Replace，避免替代环。
            if (ctx.TargetDirty)
            {
                ctx.TargetDirty = false;
                if (!_targetValidator.IsValid(ctx))
                {
                    ctx.Fizzled = true;
                    break;
                }
            }

            stage.Apply(ctx);
        }

        return ctx.ToResult(chainDepth);
    }
}
```

### 3.2 替代 / 转移

```csharp
public interface IDamageReplacement
{
    int Priority { get; }
    bool CanReplace(DamageContext ctx);
    void Replace(DamageContext ctx); // 可改 Amount / Target / Kind / Tags
}

public sealed class ReplaceStage : IDamageStage
{
    public const int MaxDepth = 4;
    private readonly List<IDamageReplacement> _replacements;

    public int Order => DamageStageOrder.Replace;

    public void Apply(DamageContext ctx)
    {
        foreach (var r in _replacements.OrderBy(x => x.Priority))
        {
            if (ctx.ReplacementDepth >= MaxDepth) break;
            if (!r.CanReplace(ctx)) continue;

            r.Replace(ctx);
            ctx.ReplacementDepth++;
            ctx.TargetDirty = true; // 改数量时复检也无害；改目标时必须
        }
    }
}

public sealed class RedirectPolicy
{
    public int MaxDepth = 1;                 // 默认一层守护改写
    public bool RevalidateAfterRedirect = true;
    public bool ReapplyReplacements = false; // 默认不重跑替代
}

public interface IDamageRedirect
{
    int Priority { get; }
    bool TryRedirect(DamageContext ctx, out Entity newTarget);
}

public sealed class RedirectStage : IDamageStage
{
    private readonly List<IDamageRedirect> _redirects;
    private readonly RedirectPolicy _policy;

    public int Order => DamageStageOrder.Redirect;

    public void Apply(DamageContext ctx)
    {
        while (ctx.RedirectDepth < _policy.MaxDepth)
        {
            IDamageRedirect hit = null;
            Entity next = null;
            foreach (var r in _redirects.OrderBy(x => x.Priority))
            {
                if (r.TryRedirect(ctx, out var candidate))
                {
                    hit = r;
                    next = candidate;
                    break;
                }
            }

            if (hit == null) break;

            ctx.Target = next;
            ctx.RedirectDepth++;
            if (_policy.RevalidateAfterRedirect)
                ctx.TargetDirty = true;
        }
    }
}
```

### 3.3 增幅 / 防护 / 最终修改

```csharp
public interface IDamageModifier
{
    int Stage { get; }      // Amplify / FinalModify
    int Priority { get; }
    bool Applies(DamageContext ctx);
    void Apply(DamageContext ctx);
}

public interface IPreventionLayer
{
    int Priority { get; }
    int Prevent(DamageContext ctx, int amount); // 返回剩余量
}

public sealed class AmplifyStage : IDamageStage
{
    private readonly List<IDamageModifier> _mods;
    public int Order => DamageStageOrder.Amplify;

    public void Apply(DamageContext ctx)
    {
        foreach (var m in _mods.Where(x => x.Stage == DamageStageOrder.Amplify).OrderBy(x => x.Priority))
            if (m.Applies(ctx)) m.Apply(ctx);
    }
}

public sealed class PreventStage : IDamageStage
{
    private readonly List<IPreventionLayer> _layers;
    public int Order => DamageStageOrder.Prevent;

    public void Apply(DamageContext ctx)
    {
        int before = ctx.Amount;
        foreach (var layer in _layers.OrderBy(x => x.Priority))
        {
            if (ctx.Amount <= 0) break;
            ctx.Amount = layer.Prevent(ctx, ctx.Amount);
        }
        ctx.Prevented += before - ctx.Amount;
    }
}

public sealed class FinalModifyStage : IDamageStage
{
    private readonly List<IDamageModifier> _mods;
    public int Order => DamageStageOrder.FinalModify;

    public void Apply(DamageContext ctx)
    {
        // 全挡默认不进入最终修改（易损不放大、不消耗）
        if (ctx.Amount <= 0) return;
        foreach (var m in _mods.Where(x => x.Stage == DamageStageOrder.FinalModify).OrderBy(x => x.Priority))
            if (m.Applies(ctx)) m.Apply(ctx);
    }
}
```

防护层保持「层内按优先级串行」；圣盾、护甲、坚韧是三个 `IPreventionLayer`，新防御关键词注册即可，不改管线。

### 3.4 扣血

```csharp
public interface IDamageApplier
{
    AppliedDamage Apply(DamageContext ctx);
}

/// <summary>生命支付/流失：非伤害路径，只受生命锁/上限影响；
/// 不触发圣盾/护甲/坚韧/吸血/系命/报复/荆棘。</summary>
public interface ILifeLossService
{
    int Apply(Entity target, int amount, DeathCause cause, Entity source);
}

/// <summary>致死锁存：ApplyStage 置位，SBA checkpoint 消费。
/// 置位后吸血/治疗不能清除；实体仍可结算已触发的报复（濒死反咬），
/// 但不再触发新的吸血/系命/报复。</summary>
public interface IPendingDeath
{
    bool IsPendingDeath { get; }
    void MarkPendingDeath(DeathCause cause, Entity source);
}

public readonly struct AppliedDamage
{
    public readonly int Dealt;
    public readonly bool Lethal;
    public AppliedDamage(int dealt, bool lethal) { Dealt = dealt; Lethal = lethal; }
}

public sealed class ApplyStage : IDamageStage
{
    private readonly IDamageApplier _applier;
    public int Order => DamageStageOrder.Apply;

    public void Apply(DamageContext ctx)
    {
        var applied = _applier.Apply(ctx);
        ctx.Dealt = applied.Dealt;
        ctx.Lethal = applied.Lethal;
        if (applied.Lethal && ctx.Target is IPendingDeath pending)
            pending.MarkPendingDeath(DeathCause.DamageLethal, ctx.Source);
        // 不在这里 IsAlive=false；死亡交给 SBA checkpoint
    }
}
```

`ApplyStage` 只调 `IDamageApplier`，把 `Dealt`/`Lethal` 写回 `ctx`；**不**在这里 `IsAlive=false`。死亡由 `DamageAftermath` 之后的 SBA checkpoint 处理。

### 4.2 规则顺序（默认）

| Priority | 规则 | 行为 | 后续 |
|---:|---|---|---|
| 100 | 事件发布 | `DamageEvent` → `CombatDamageEvent` → `LifeChangeEvent` | 无 |
| 200 | 吸血/系命 | 按 `Dealt` 回复；**不回 `LoopCost.Life`** | 无 |
| 300 | 荆棘 | 层数减半，造成等量伤害 | `FollowUpEvent`（`Halve`） |
| 400 | 报复 | 对来源造成等量伤害 | `FollowUpEvent`（`UntilDeath` + `Life(1)`） |
| 500 | 病原体 | 来源加毒素 | 无 |
| 600 | 剧毒 | 战斗伤害且目标存活 → 消灭 | 无 |

> 顺序可变，但**必须由规则声明**，不再由 `ApplyDamage` 的物理段序决定。

### 4.3 铁律

- Aftermath **不许**直接调 `ApplyDamage`；只 `Enqueue`。
- `IAftermathContext.Enqueue` 的实现必须先调 `DamageChain.CanEnqueue`——`OneBounce` 兼容档就在这里拦，不要在每个关键词里各写一个 guard。
- 报复/荆棘的后续伤害是新的 `DamageRequest`，走完整管线（对方圣盾/护甲/坚韧照常拦截）。
- 致死伤害的 Aftermath 仍然执行（`Dealt>0`），所以「濒死反咬」成立；SBA checkpoint 之后不再产生新触发。
- `PendingDeath` 实体不再触发吸血/系命（它已经死了，只是还没送墓）。否则 SBA 前的治疗会制造新的循环，血量势函数失效。
- `LifeCost` 走独立 `LifePayment`/`LifeLoss` 路径，不经过 `DamagePipeline`，不被吸血/系命/圣盾/护甲响应。

## 5. 循环链（DamageChain）

### 5.1 上下文

```csharp
public enum ChainOutcome
{
    Resolved,
    Fizzled,
    Lethal,
    BudgetExhausted,
    StateRepeat,
    Stalemate,
}

public sealed class ChainContext
{
    public DamageRequest Root;
    public ChainPolicy Policy;
    public int EventCount;
    public int Depth;
    public readonly HashSet<(Entity Target, string Keyword)> Visited = new();
    public readonly Dictionary<Entity, int> StartLife = new(); // v1 备用：吸血上限/状态哈希
    public readonly Dictionary<Entity, int> LifePaid = new();
    public readonly List<DamageLogEntry> Log = new();
    public ChainOutcome Outcome;

    private readonly HashSet<ulong> _seenHashes = new();

    // Visited 只给传播类关键词（Splash/Overwhelm）用；
    // 报复/荆棘靠 LoopCost/衰减收敛，不靠 Visited，否则互弹一次就被挡住。
    public bool TryVisit(Entity target, string keyword)
    {
        if (Policy.AllowRevisit) return true;
        return Visited.Add((target, keyword));
    }

    // v1 只用根事件的 Source/Target 判断；多目标链由调用方另给 IChainTermination。
    public bool IsAllDead()
    {
        bool sourceDead = Root?.Source == null || !Root.Source.IsAlive;
        bool targetDead = Root?.Target == null || !Root.Target.IsAlive;
        return sourceDead && targetDead;
    }

    public bool HasStateRepeated(IChainStateHasher hasher)
    {
        return !_seenHashes.Add(hasher.Hash(this));
    }
}
```

### 5.2 策略与代价

```csharp
public enum LoopPolicy
{
    OneBounce,      // 兼容档：报复伤害不再触发报复（当前 guard 语义）
    UntilDeath,     // 循环到参与者死亡/目标失效（报复默认）
    Halve,          // 每代伤害/层数减半（荆棘）
    ConsumeCounter, // 每次后续消耗可见指示物
    ChainBudget,    // 只靠预算/Visited 收口
}

public enum LoopCostKind { None, Life, Counter, Durability }

public readonly struct LoopCost
{
    public readonly LoopCostKind Kind;
    public readonly int Amount;
    public readonly string CounterId;

    public LoopCost(LoopCostKind kind, int amount, string counterId = null)
    {
        Kind = kind; Amount = amount; CounterId = counterId;
    }

    public static LoopCost None => new(LoopCostKind.None, 0);
    public static LoopCost Life(int n) => new(LoopCostKind.Life, n);
    public static LoopCost Counter(string id, int n) => new(LoopCostKind.Counter, n, id);
    public static LoopCost Durability(int n) => new(LoopCostKind.Durability, n);
}

public sealed class ChainPolicy
{
    public LoopPolicy Loop = LoopPolicy.UntilDeath;
    public LoopCost Cost = LoopCost.None;

    // 安全断言，不是玩法：命中即记日志并结束，不静默截断。
    public int MaxEvents = 256;
    public int MaxDepth = 64;

    public bool AllowRevisit = false;       // 传播类默认 false；报复设 true
    public bool StopOnStateRepeat = true;   // 严格循环检测
    // 替代/转移深度不放在 ChainPolicy：分别由 ReplaceStage.MaxDepth 与
    // RedirectPolicy.MaxDepth 管，避免两处配置打架。
}
```

策略落地位置：

| 策略 | 落地 |
|---|---|
| `OneBounce` | `DamageChain.CanEnqueue` 拦截 `Generation>0` 的 `Retaliate`；等价现有 `_retaliateBounceGuard` |
| `UntilDeath` | 允许报复入队；靠 `LoopCost`/生命收敛，不用 `Visited` |
| `Halve` | Aftermath 生成 `FollowUpEvent` 时 `Amount = ceil(Amount/2)`；荆棘层数同步减半 |
| `ConsumeCounter` | `LoopCost.Counter(id,n)`，由 `PayLoopCost` 扣 |
| `ChainBudget` | 只靠 `MaxEvents`/`Visited`，用于特殊卡 |

> v1 只实现 `LoopCost.None` 与 `LoopCost.Life`；`Counter`/`Durability` 是预留位。它们应在伤害前支付（付不起就不产生后续事件），接入时单独定顺序，不能沿用 Life 的「后付」。

### 5.4 Pump 伪代码

```csharp
public sealed class DamageChain
{
    private readonly Queue<FollowUpEvent> _queue = new();
    private readonly DamagePipeline _pipeline;
    private readonly IAftermathEngine _aftermath;
    private readonly IChainSba _sba;
    private readonly IChainStateHasher _hasher;
    private readonly IChainLog _log;
    private readonly ILifeLossService _lifeLoss;

    public ChainOutcome Run(DamageRequest root, ChainPolicy policy)
    {
        var ctx = new ChainContext { Root = root, Policy = policy };
        _queue.Enqueue(new FollowUpEvent
        {
            Request = root,
            Policy = policy,
            Owner = root.Source,
            Origin = root.Source,
            Keyword = "Root",
            Generation = 0,
        });
        return Pump(ctx);
    }

    // Aftermath 的 Enqueue 应经过此门；OneBounce 就是当前报复 guard 的兼容实现。
    // 约定：根事件 Generation=0，第一代报复=1，报复互弹=2+。
    public bool CanEnqueue(FollowUpEvent ev)
    {
        if (ev.Policy.Loop == LoopPolicy.OneBounce
            && ev.Keyword == KeywordRules.Retaliate
            && ev.Generation > 1)
            return false;
        return true;
    }

    private ChainOutcome Pump(ChainContext ctx)
    {
        while (_queue.Count > 0)
        {
            if (ctx.EventCount >= ctx.Policy.MaxEvents)
            {
                _log.BudgetExhausted(ctx);
                return ChainOutcome.BudgetExhausted;
            }

            var ev = _queue.Dequeue();
            if (ev.Generation > ctx.Policy.MaxDepth)
            {
                _log.DepthExhausted(ctx, ev);
                return ChainOutcome.BudgetExhausted;
            }

            ctx.EventCount++;
            ctx.Depth = ev.Generation;

            if (!IsValid(ev))
            {
                _log.Fizzled(ctx, ev);
                continue;
            }

            // 1. 结算伤害
            var result = _pipeline.Resolve(ev.Request, ev.Generation);

            // 2. 后效：事件、吸血、荆棘/报复入队……
            if (!result.Fizzled)
                _aftermath.Process(result, ctx);

            // 3. 支付循环代价（默认在伤害与吸血之后；v1 只实现 Life/None）
            PayLoopCost(ev, ctx);

            // 4. SBA checkpoint：死亡/送墓/亡语
            _sba.Checkpoint();
            if (ctx.IsAllDead()) return ChainOutcome.Lethal;

            // 5. 严格循环检测
            if (ctx.Policy.StopOnStateRepeat && ctx.HasStateRepeated(_hasher))
            {
                _log.StateRepeat(ctx);
                return ChainOutcome.StateRepeat;
            }
        }

        return ChainOutcome.Resolved;
    }

    private bool IsValid(FollowUpEvent ev)
    {
        // 只校验 Target：已入队的「濒死反咬」即使 Source 已死也允许结算；
        // 新的后续事件由 Aftermath 的 Source.IsAlive 门禁拦截。
        return ev.Request != null
            && ev.Request.Target != null
            && ev.Request.Target.IsAlive;
    }

    private bool PayLoopCost(FollowUpEvent ev, ChainContext ctx)
    {
        // 根事件不付循环代价；代价只属于后续事件。
        // 已死 Owner 不再付血债（已触发的反噬仍结算，但死亡后不再计费）。
        if (ev.Keyword == "Root"
            || ev.Owner == null
            || !ev.Owner.IsAlive
            || ev.Policy.Cost.Kind == LoopCostKind.None)
            return true;

        switch (ev.Policy.Cost.Kind)
        {
            case LoopCostKind.Life:
                ctx.LifePaid[ev.Owner] = ctx.LifePaid.GetValueOrDefault(ev.Owner) + ev.Policy.Cost.Amount;
                // 生命支付，不是伤害：不进 DamagePipeline，不被吸血/系命/圣盾/护甲响应。
                _lifeLoss.Apply(ev.Owner, ev.Policy.Cost.Amount, DeathCause.LifePayment, ev.Origin);
                return ev.Owner.IsAlive;

            case LoopCostKind.Counter:
                int have = ev.Owner.GetCounterCount(ev.Policy.Cost.CounterId);
                if (have < ev.Policy.Cost.Amount) return false;
                ev.Owner.AddCounters(ev.Policy.Cost.CounterId, -ev.Policy.Cost.Amount, ev.Origin);
                return true;

            case LoopCostKind.Durability:
                CounterRules.LoseDurability(GameCore.Instance, ev.Owner as Card,
                    ev.Policy.Cost.Amount, "循环代价");
                return ev.Owner.IsAlive;

            default:
                return true;
        }
    }
}
```

### 5.5 死亡时点

- Aftermath 在 SBA 前：致死伤害的报复**仍会入队**，这是「濒死反咬」。
- SBA checkpoint 之后：死者不再产生新的后续事件；已在队列里的后续事件如果 **Target** 已死，`IsValid` 失败 → fizzle。
- 已入队的 `FollowUpEvent` 允许 `Source` 已死（这是「已触发的能力」而不是「新触发」）；新事件是否入队由 Aftermath 的 `Source.IsAlive` 门禁决定。**这两件事不能混。**
- 是否需要「死亡先于触发」作为可选策略？`ChainPolicy.DeathBeforeTrigger`（默认 false）留给后续扩展；v1 不做。

### 6.1.1 具体规则：报复

```csharp
public sealed class RetaliateAftermathRule : IAftermathRule
{
    public int Priority => 400;

    public bool Applies(DamageResult r) =>
        r.Dealt > 0
        && r.Source != null
        && r.Source.IsAlive              // 来源已死不反噬（同现有门）
        && !(r.Source is IPendingDeath pd && pd.IsPendingDeath) // 濒死来源不再产生新反噬
        && !ReferenceEquals(r.Source, r.FinalTarget)
        && r.FinalTarget.HasKeyword(KeywordRules.Retaliate);

    public void Apply(DamageResult r, IAftermathContext ctx)
    {
        var followUp = new FollowUpEvent
        {
            Request = new DamageRequest
            {
                Source = r.FinalTarget,   // 反噬者
                Target = r.Source,        // 伤害来源
                Amount = r.Dealt,         // 等量
                Kind = DamageKind.Effect,
                Tags = DamageTags.Retaliate | DamageTags.Chain,
            },
            Policy = new ChainPolicy
            {
                Loop = ctx.Chain.Policy.Loop, // 继承根策略：旧卡 OneBounce，新卡 UntilDeath
                // OneBounce 必须与 Legacy 完全一致：不付血债；UntilDeath 才付 Life(1)。
                Cost = ctx.Chain.Policy.Loop == LoopPolicy.OneBounce
                    ? LoopCost.None
                    : LoopCost.Life(1),
                AllowRevisit = true,          // 不靠 Visited 挡互弹
                StopOnStateRepeat = true,
                MaxEvents = 256,
            },
            Owner = r.FinalTarget,        // 血债由反噬者支付
            Origin = r.FinalTarget,
            Keyword = KeywordRules.Retaliate,
            Generation = r.ChainDepth + 1,
        };
        if (ctx.Chain.CanEnqueue(followUp))
        {
            // 事件口径修正：Target=反噬者，Source=伤害来源（当前实现 Source 填了 target，语义反了）
            // 只有真正入队才发事件，保证 OneBounce 兼容档与 Legacy 的事件数一致。
            ctx.Publish(new KeywordAppliedEvent
            {
                Target = r.FinalTarget,
                Keyword = KeywordRules.Retaliate,
                Detail = $"报复反噬：{EffectText.Name(r.FinalTarget)} 对 {EffectText.Name(r.Source)} 造成 {r.Dealt} 点伤害（等量）",
                Source = r.Source,
            });
            ctx.Enqueue(followUp);
        }
    }
}
```

注意：

- `Applies` 不检查 `FinalTarget.IsAlive`——致死伤害的报复仍然入队（濒死反咬）。
- 入队后即使 `FinalTarget` 已死，`DamageChain.IsValid` 也只查 `Target`，所以这条已触发的报复仍会结算；但它造成的新伤害不会再触发死者的报复（`r.Source.IsAlive` + `PendingDeath` 门）。
- 根事件不付 `LifeCost`；`PayLoopCost` 对 `Keyword == "Root"` 直接放行，只有报复/荆棘这类后续事件付代价。
- `PendingDeath` 的 Source 只结算已入队的反噬，不再产生新的反噬；这是链在死亡处收口的第二道门（第一道是 Target 已死 fizzle）。

### 6.2 为什么是 `Life(1)`

- 报复的伤害本身由血量承担；吸血可以把这次伤害补回来。
- 如果没有任何「吸血补不回」的部分，报复 + 吸血就是严格循环：双方每轮满血，`StateRepeat` 会命中，链只能判平或硬停。
- `Life(1)` 是血债：每次报复触发，反噬者先结算伤害与吸血，再失去 1 点生命（`LifePayment`，不进伤害管线，不被吸血/系命/圣盾/护甲响应）。
- 每轮完整循环的净生命变化 = `-Life(1)`，与伤害大小无关；血量成为势函数，链必然有限。
- 链长大致 = 参与者生命 / `LifeCost`（再受伤害、吸血、防御修正）；3 血约 3 轮，10 血约 10 轮——这是可调的节奏旋钮，不是隐藏上限。
- 这不是给报复加一个局部特判，而是 `LoopCost` 的通用策略；其他卡可以用 `Life(n)`、`Counter(id,n)`、`Durability(n)` 或 `None`。

### 6.3 结算顺序

```
伤害 → 吸血/系命 → 支付 LoopCost（LifePayment）→ SBA checkpoint
```

先伤害后血债，保证「本次反噬仍然生效」；血债致死时，本次反噬已经打出，不会因为付不起而回滚。这是「濒死反咬」的口径。

### 6.4 3 血 1 伤样例

双方 3 血、1 攻、报复 + 吸血，A 先打 B：

| 步 | 事件 | 生命 | 说明 |
|---:|---|---|---|
| 0 | A→B 1 | B 3→2 | 根伤害 |
| 1 | B 报复 | A 3→2；B 吸血 +1 →3；B 血债 −1 →2 | 伤害、吸血、血债 |
| 2 | A 报复 | B 2→1；A 吸血 +1 →3；A 血债 −1 →2 | 交替 |
| 3 | B 报复 | A 2→1；B 吸血 +1 →2；B 血债 −1 →1 | |
| 4 | A 报复 | B 1→0（致命）；A 吸血 +1 →2；A 血债 −1 →1 | B 死 |
| 5 | B 的已触发报复 | A 1→0；B 已死，吸血/血债按死亡规则 | 双死，链停 |

> 精确步数取决于死亡时点与吸血上限；上表用于对拍，不作为唯一结果。测试要断言「有限步内结束 + 总生命单调不增 + 无预算命中」。

### 6.5 如果某张卡要真正的无限循环

```csharp
Loop = LoopPolicy.UntilDeath,
Cost = LoopCost.None,
StopOnStateRepeat = true,
MaxEvents = 256,
```

- 状态重复（生命/指示物/区域/关键词完全一致）→ `StateRepeat`，链结束，记日志；不静默跑 30 次。
- 状态不重复但很长 → `MaxEvents` 断言；这是 bug/组合异常，不是玩法。
- 如果未来要做「玩家选择重复 N 次」的快捷结算，`StateRepeat` 是接入点。

## 7. 兼容与迁移

### 7.1 Resolver 双实现

```csharp
public interface IDamageResolver
{
    DamageResult Resolve(DamageRequest request);
}

public sealed class LegacyDamageResolver : IDamageResolver
{
    // 直接调 ApplyDamageLegacy（原 ApplyDamage 实现），行为零漂移
}

public sealed class ChainDamageResolver : IDamageResolver
{
    // DamagePipeline + DamageAftermath + DamageChain
}

public static class DamageResolverRegistry
{
    public static IDamageResolver For(Entity source, Entity target)
    {
        // 默认 Legacy；卡/关键词显式 opt-in 才走 Chain
        // 例：CardData.ResolutionMode == ResolutionMode.Chain
        return IsChainOptIn(source, target)
            ? ChainResolver
            : LegacyResolver;
    }

```

`KeywordRules.ApplyDamage` 保留签名，内部改为 facade；当前实现改名 `ApplyDamageLegacy`，`LegacyDamageResolver` 调它：

```csharp
// 当前实现原样保留，改名；guardRerouted 只在旧递归内部使用。
public static int ApplyDamageLegacy(Entity source, Entity target, int amount, bool isCombat, bool guardRerouted = false)
{
    // ... 现有 ApplyDamage 全部逻辑 ...
}

public static int ApplyDamage(Entity source, Entity target, int amount, bool isCombat, bool guardRerouted = false)
{
    // 外部入口默认 guardRerouted=false；该参数只服务旧守护递归，
    // 新 Chain 路径用 RedirectPolicy 替代，不再使用它。
    var request = new DamageRequest
    {
        Source = source,
        Target = target,
        Amount = amount,
        Kind = isCombat ? DamageKind.Combat : DamageKind.Effect,
        Tags = DamageTags.None,
    };
    var result = DamageResolverRegistry.For(source, target).Resolve(request);
    return result.Dealt;
}
```

`LegacyDamageResolver` 内部直接调 `ApplyDamageLegacy`，所以旧守护递归、`_retaliateBounceGuard`、30 次闸、现有段序全部保持；新 Chain 路径不经过这个方法。

> 迁移红线：`ApplyDamageLegacy` 内部所有自递归（守护改写、荆棘、报复）也必须改成调 `ApplyDamageLegacy`。否则同一张旧卡会一半走 Legacy、一半走 facade，行为不可预测。

### 7.2 旧卡默认行为

- 旧卡 `ResolutionMode = Legacy`，走 `LegacyDamageResolver`，连 `_retaliateBounceGuard`、30 次闸、现有顺序都不变。
- 新卡/新关键词显式 `Chain`，才启用 `UntilDeath`/`LoopCost`/`Visited`。
- 旧卡如果未来要切 Chain，先用 `LoopPolicy.OneBounce` 对拍，确认与 Legacy 一致后再切 `UntilDeath`。

### 7.3 迁移顺序

1. **抽接口，不换实现**：加 `IDamageResolver`、`DamageRequest`、`DamageResult`，Legacy 包装现有 `ApplyDamage`。全绿。
2. **抽 Pipeline**：把 `ApplyDamage` 的层逐步搬进 `DamageStage`；每搬一层跑 golden。Legacy 仍可走旧实现做对照。
3. **抽 Aftermath**：事件/吸血/荆棘/报复/病原体/剧毒改成 `IAftermathRule`；默认 `OneBounce`，行为不变。
4. **上 Chain**：新卡 opt-in `UntilDeath` + `Life(1)`；旧卡继续 Legacy。
5. **上传播边**：碾压/溅射只开显式边，`Visited` 保证有限。
6. **删旧块**：`_retaliateBounceGuard`、`splashed` 局部集合、`ApplyDamage` 里的关键词分支逐个删除；30 次闸降级为 Legacy 的断言。

### 7.4 Golden 对拍

对每个迁移场景记录：

```
(scenarioId) → { Dealt, LifeAfter, Counters, Events[], Deaths[], ChainOutcome }
```

Legacy 与 Chain(`OneBounce`) 必须完全一致；Chain(`UntilDeath`) 单独写期望值。

必测场景：

- 单次伤害：圣盾/护甲/坚韧/暴击/易损/生命锁。
- 替代改目标、守护改写、替代+守护叠加。
- 报复 1v1（无吸血、有吸血、有荆棘）。
- 报复 + 吸血 + 生命锁。
- 碾压 + 溅射（`Visited`、每个目标一次）。
- 致死伤害的濒死反咬；死后不再触发。
- 全挡时易损不消耗；减半护盾与暴击的取整。
- 预算/状态重复命中时日志完整、不崩、不静默。

## 8. 传播边（碾压/溅射，可选）

`Visited` 只用于传播类关键词；每条边显式声明：

| 源事件 | 关键词 | 目标 | 策略 |
|---|---|---|---|
| 主战斗伤害 | `Overwhelm` | 宣言目标左右邻格 | `Visited`，每目标每链一次 |
| 主战斗伤害/碾压 | `Splash` | 随机对手单位（溢出） | `Visited`，每目标每链一次，溢出递减 |
| 任意伤害 | `Retaliate` | 伤害来源 | `UntilDeath` + `Life(1)`，不用 `Visited` |
| 任意伤害 | `Thorns` | 伤害来源 | `Halve`，不用 `Visited` |
| 任意伤害 | `Pathogen` | 伤害来源 | 一次，加毒素 |

不做全连通：`Splash` 伤害默认不再触发 `Overwhelm`，除非显式加边并配 `Generation` 衰减。全连通是组合爆炸；选定边是可控设计。

## 11. 每卡 30 次 → 过载指示物（2026-11-09 裁定）

### 11.1 裁定

- 30 次闸按**卡实例**计数：同一张卡，不管挂几个效果、主动还是自动，一回合累计发动/触发 **30 次**后挂系统指示物「过载」。
- 过载效果：该卡的**主动效果、自动效果、自动触发型关键词**失效；攻击/守卫按主动效果处理，拒绝宣言。
- 过载是系统级指示物，不可净化、不可换区清除，只在下回合开始移除。
- 30 闸是最后一道系统断言，不是循环收敛；`LoopCost`/`StateRepeat` 仍负责让链自然结束。

### 11.2 计数范围

计入：

- 组合出来的**主动**效果（`Activate_*`）。
- 组合出来的**自动/被动触发**效果（`TriggerTiming.*`，含 `OnPlay/OnSummon/OnDeath` 等）。
- **攻击宣言**、**守卫宣言**：按主动效果计，1 次/次。
- **高危 11 相关的关键词**（见 11.2.1）。
- **光环赋予的效果**：计入**受益者**（见 11.2.2），不计入光环本体。

不计入：

- **所有指示物**：圣盾、护甲、坚韧、易损、毒素、荆棘、潜行、法术护盾、生命锁、无实体、复生、冻结、沉睡、+1/+1、攻防、费用、耐久、倒计时、死亡计数、临时、诅咒、祝福、反疗、重放、沉默、失效、展示、变形、突袭紊乱等——它们有自己的 tick/消耗/换区规则，**完全移出** 30 计数与过载压制。
- **耐久支付**本身（结界的自动组合效果仍按自动效果计）。
- **非高危关键词**：先攻、连击、缴械、警戒、不灭、绝缘体等。
- 卡牌施放本身（cast 不是效果发动）。
- 系统动作：充能、地牌横置产费、回合/阶段推进。
- 强制分支引擎（倒计时/运势等）——暂不计。

> 关键：荆棘是 `RetaliationCounter`（指示物），不是关键词，**不计入**；圣盾/护甲/坚韧/易损/毒素同理。不要把它们再塞回 30 闸。

### 11.2.1 高危 11 相关关键词白名单（计入）

> 只收**关键词**；指示物已完全移出。实现上给 `KeywordDefinition.CountsTowardOverload` 开关，逐项可调。

| 高危时机 | 计入关键词 |
|---|---|
| `OnDealDamage` | 吸血、系命、暴击、剧毒、碾压、溅射 |
| `OnTakeDamage` | 报复、病原体、剧毒 |
| `OnTargeted` | 守护、帷幕、隐密 |
| `OnAtomicEffectActivation` / `OnAtomicEffectStartApplying` / `OnAtomicEffectResolution` | 上述关键词被原子施加/触发时 |
| `OnDraw` / `OnScry` / `OnCardPlayed` / `OnSpellCast` / `OnCardCastSettled` | 无专属关键词；组合效果本身已计 |

> 荆棘（RetaliationCounter）、圣盾、护甲、坚韧、易损、毒素、潜行、法术护盾、生命锁、无实体、复生等**不是关键词**，一律不计。它们靠自己的层数/消耗/回合末规则收敛；如果某个指示物未来变成「不消耗、可无限自触发」的循环引擎，再单独给它开 `CountsTowardOverload`，不要现在一刀切。

### 11.2.2 光环赋予的效果算谁

- 当前引擎：`TriggerEngine.EnumerateAuraGrantedEffects` 合成 `RegisteredEffect` 时 `Source = 受益者`、`Controller = 受益者控制者`、`FromAuraGrant = true`。按 Source 计数 = **受益者**。
- 光环本体是持续效果，不「发动」、不计数；光环本体自己若有主动/触发效果，才算它自己。
- 受益者过载 → 它身上的授予效果失效；其他受益者、光环本体不受影响。不要算到光环本体，否则一个光环给 5 个单位，会被一个单位的循环拖垮。
- 现有 `FromAuraGrant` 豁免 `失效/沉睡` 的口径**不自动适用**于过载：过载是受益者的使用预算，应该压受益者；如果要让光环授予免疫过载，需要显式豁免。
- 边界：授予对象是玩家（非卡）时没有 Card 预算；**默认跳过计数**（不记到光环本体，也不压玩家）。

### 11.3 计数单位

- 1 次 = 1 个效果发动/触发，不是 1 个原子、1 个目标、1 段伤害。
- 组合效果 3 个原子 = 1；攻击 1 次 = 1；守卫 1 次 = 1；触发式每入队 1 条 = 1；高危关键词每次触发 = 1。
- 触发式在入队/入栈口计数；主动在成功入栈后计数；攻击/守卫在宣言成功后计数。
- **高危关键词在效果结算之后提交计数**——否则第 30 次刚挂上过载，会把自己的效果压掉；主动/触发在入栈/入队时提交，结算本身不受本次过载影响。
- 发动无效/效果无效按 `RefundUse` 退款；退款后若计数 <30，移除过载（边界情况，记日志）。
- **第 30 次本身照常结算**；它结算过程中产生的新主动/自动效果会被过载挡住（计数已到 30）。

### 11.4 过载指示物

- `CounterRules.OverloadCounter = "Overload"`：`CounterClass.System`、`CounterPolarity.Negative`、`TickPolicy = External`、`DisplayName = "过载"`。
- 挂载：`CardEffectBudget.Commit` 达到 30 时 `card.AddCounters(OverloadCounter, 1, card)`，发 `CounterChangedEvent` + `CardOverloadedEvent`。
- 移除：下回合开始 `CardEffectBudget.OnNewTurn` 按「已挂卡清单」统一移除，并清计数。净化/换区默认**不移除**（系统冻结）；如果要做成可交互，另开规则。
- 实现注意：`CounterRules.ClearCounters` 的换区/净化通用口会清 System 指示物；必须给 `OverloadCounter` 开例外，否则卡一换区/一净化，过载就掉了。
- 读取：`SuppressRules.IsOverloaded(Entity)` 只读指示物层；**不受绝缘体影响**（System 指示物豁免）。`IsAutoSuppressed(Entity)` 要先查 overload，再走绝缘体豁免——否则绝缘体会把系统冻结也免掉。
- 主动闸：`CanActivate` / `EffectEligibility` / `ActivateEffect` 先查 `IsOverloaded`，拒绝 reason「过载：本回合主动/自动效果已失效」。
- 自动闸：`TriggerEngine.FindMatchingEffects` 与 `SuppressRules.IsAutoSuppressed` 查 `IsOverloaded`；触发式丢弃，强制触发也丢并记 `MandatorySkipped`。
- 攻击/守卫：`CombatSystem.TryDeclareAttack`、`GameActions.DeclareAttack`、守卫宣言入口查 `IsOverloaded`，拒绝；已宣言的照常结算，不再新增。
- UI/AI：候选枚举/LAE/SimpleAI 预检 `IsOverloaded`；卡面显示「过载」图标与 `30/30`。
- 联机：快照带 `EffectBudgetCount` / `Overload` 指示物，服务器权威。

### 11.5 过载压制范围

- **组合主动/自动效果**：失效。
- **自动触发型关键词**：失效。报复、病原体、剧毒、吸血、系命、暴击、碾压、溅射、狩猎、再生等在过载期间不触发。
- **指示物**：**不压**。圣盾、护甲、坚韧、易损、毒素、荆棘、潜行、法术护盾、生命锁、无实体、复生、+1/+1、费用、耐久等按自己的 tick/消耗/换区规则继续工作。
- **非触发型关键词**：仍生效。先攻、连击、缴械、警戒、守护、不灭、绝缘体、帷幕等是静态规则，不是「自动触发」。
- **攻击/守卫**：拒绝宣言（按主动效果失效）；已宣言的照常结算，不再新增。

> 实现上不要把 `IsOverloaded` 塞进 `HasKeyword` 的全局读——那会连静态关键词/条件判断一起压掉。压制口放在：主动闸、触发队列、高危关键词执行点、攻击/守卫入口。

### 11.6 接口

```csharp
public enum CardEffectCommitKind { Active, Triggered, Attack, Guard, Keyword }

public sealed class CardEffectBudget
{
    public const int Limit = 30;
    private readonly Dictionary<Card, int> _count = new();
    private readonly HashSet<Card> _overloaded = new(); // 仅用于回合末清指示物

    public int Count(Card card) => card != null && _count.TryGetValue(card, out var n) ? n : 0;

    public bool IsOverloaded(Card card)
        => card != null && card.GetCounterCount(CounterRules.OverloadCounter) > 0;

    public bool CanCommit(Card card, out string reason)
    {
        reason = null;
        if (card == null) return true;
        if (IsOverloaded(card))
        {
            reason = "过载：本回合主动/自动效果已失效";
            return false;
        }
        return true;
    }

    public bool Commit(Card card, CardEffectCommitKind kind, out string reason)
    {
        if (!CanCommit(card, out reason)) return false;

        int n = Count(card) + 1;
        _count[card] = n;

        if (n >= Limit && !IsOverloaded(card))
        {
            card.AddCounters(CounterRules.OverloadCounter, 1, card);
            _overloaded.Add(card);
            EventManager.Instance.Publish(new CardOverloadedEvent
            {
                Card = card, Count = n, Kind = kind
            });
        }

        EventManager.Instance.Publish(new CardEffectBudgetChangedEvent
        {
            Card = card, Count = n, Overloaded = IsOverloaded(card)
        });
        return true;
    }

    public void Refund(Card card)
    {
        if (card == null) return;
        int n = Count(card);
        if (n <= 0) return;

        n--;
        if (n <= 0) _count.Remove(card); else _count[card] = n;

        if (n < Limit && IsOverloaded(card))
        {
            int layers = card.GetCounterCount(CounterRules.OverloadCounter);
            if (layers > 0) card.AddCounters(CounterRules.OverloadCounter, -layers, card);
            _overloaded.Remove(card);
        }

        EventManager.Instance.Publish(new CardEffectBudgetChangedEvent
        {
            Card = card, Count = n, Overloaded = IsOverloaded(card)
        });
    }

    public void OnNewTurn(int turnNumber)
    {
        foreach (var card in _overloaded)
        {
            int layers = card?.GetCounterCount(CounterRules.OverloadCounter) ?? 0;
            if (layers > 0) card.AddCounters(CounterRules.OverloadCounter, -layers, null);
        }
        _overloaded.Clear();
        _count.Clear();
    }
}
```

事件字段：`Card`、`Count`、`Overloaded`、`Kind`、`Reason`（过载原因/第 30 次的来源）。

挂载点：`GameCore` 单例（或 `EffectExecutor` 持有），由 `GameCore.OnTurnStarted` 调 `OnNewTurn`；所有入口经 `GameCore.Instance.CardEffectBudget` 访问，避免各系统各持一份计数。

### 11.7 接入点

| 入口 | 位置 | 检查 | 记账 |
|---|---|---|---|
| 触发式 | `StackEngine.ProcessTriggeredEffects` | `CanCommit` | `Commit(Triggered)`；失败丢弃 |
| 主动 | `GameActions.ActivateEffect` / `ActivateEffectInResponse` | 入栈前 `CanCommit` | 成功后 `Commit(Active)` |
| 攻击宣言 | `GameActions.DeclareAttack` / `CombatSystem.TryDeclareAttack` | `IsOverloaded` | 成功后 `Commit(Attack)` |
| 守卫宣言 | `GameActions`/`CombatSystem` 守卫入口 | `IsOverloaded` | 成功后 `Commit(Guard)` |
| 结界自动组合 | `StackEngine.ProcessTriggeredEffects` 耐久扣除前 | `CanCommit` | `Commit(Triggered)`；失败不扣耐久 |
| 高危关键词 | `KeywordRules.ApplyDamage` 6.5b/6.6/7、`CombatSystem.ResolvePair` 碾压/溅射 | 结算前 `CanCommit` | 结算后 `Commit(Keyword)`；前置失败跳过该关键词块 |

| 回合重置 | `EffectExecutor.OnNewTurn` | — | `CardEffectBudget.OnNewTurn` |

### 11.8 与现有实现的差异

- 现有 `TriggerLoopGuardReached` 键=`effect.Id@source`，只查触发式；主动/攻击/守卫/关键词都不过；耐久宿主豁免。
- 目标键=`Card`；组合主动/自动 + 攻击/守卫 + 高危关键词都过；指示物/耐久支付不过。
- 现有 `MaxTriggersPerTurnPerEffect` 保留为 per-effect 诊断/旧卡兼容；新增 `MaxCardEffectActivationsPerTurn=30` 作为硬闸。Legacy 路径可继续用旧闸，Chain/新卡走新闸；迁移完成后旧闸降级为遥测。
- 过载是**指示物**，不是内存 flag：可见、可播报、可被 UI/AI/联机快照读取；但默认不可净化、不可换区清除。

### 11.9 决议（2026-11-09 全部确认）

- 高危关键词白名单按 11.2.1 表执行（含`暴击/碾压/溅射`）。
- 指示物**完全移出**：不计入 30，也不被过载压制；按自己的 tick/消耗/换区规则走。
- 光环赋予的效果计入**受益者**，不计入光环本体；授予对象是玩家时**默认跳过计数**。
- 攻击/守卫：过载时拒绝宣言。
- 过载：不可净化、不可换区清除，只在下回合开始移除。
- 结界的自动组合效果计入；耐久支付本身不计。
- 过载计数跟随卡实例：控制权变更保留；新 token/复制体重新计数。
- 非高危关键词（先攻/连击/警戒等）不计入，也不被过载压。

> 无待确认项。实现阶段遇到新边界，另开 §11.11 记录，不回改本决议。

### 11.10 决策记录

- **指示物完全移出**：不是因为「所有指示物都衰减」（`Resident` 不衰减），而是因为能参与循环的指示物都是 `Exception/Decay`，已被层数/消耗/回合末限住；`Resident` 是静态修正，不产生循环。把它们计入 30 会造成坦克 30 次受击后圣盾/护甲失效的双重惩罚，也会把 +1/+1/费用是否压变成无意义的争论。
- **光环计受益者**：引擎现有合成条目 `Source=受益者`；光环本体是持续效果，不发动、不计数。算到光环本体会让一个单位的循环拖垮整片光环，且「光环过载」难以解释。
