## 3. 目标口径

### 3.1 什么算「值变化」

**纳入**：战场上可读数值的增减——角色生命/上限、单位攻击/生命、一切指示物层数（含护甲/圣盾/坚韧/毒素/冻结/紊乱/耐久/费用层/复生/潜行/荆棘/易损/角色攻击）、伤害、回复、疲劳、费用（手牌）、临时元素、地牌槽上限。

**不纳入（只走日志或完全不动）**：抽牌/弃牌/磨牌张数（已有行）、拼点/运势结果句、阶段/回合骨架、使用次数 (x/y)（卡面显示位）、横置/控制权、控制权类非数值状态、牌库顶信息。

### 3.2 浮字统一规格（与现役攻击浮字逐项一致）

| 项 | 值 |
|---|---|
| 载体 | 世界空间 TMP（`CreateStatsText` 单源，**不新建 UI 节点/预制体**） |
| 字号 | 6（拼点 2.25 / 运势 3 维持不动） |
| 时长/曲线 | 0.9s，easeOut 上浮 0.85，0.45s 起线性渐隐（`FloatTextAsync` 原样） |
| 锚点 | 单位 `StatsHeightY + 0.55`；角色立柱 1.9 |
| 颜色 | 增益 `StatUpColor`（#6BFF73，0.42,1,0.45）；减益 `StatDownColor`（#FF6152，1,0.38,0.32）；中性 `#E6E6E6` |
| 堆叠 | 同目标同帧多条：每条起点 +0.28 高度，最多 4 条；超出按 0.18s 间隔排队 |
| 节拍 | 伤害/回复/疲劳**保持现状**（占视觉门，属战斗节拍）；其余值浮字**不占门**（装饰层），避免多指示物拖节奏 |
| 串行 | 同单位值浮字走 `RunUnitFxAsync` 串行链（与伤害/回复同链），目标离场/不在视图静默 |

### 3.3 文案表（统一为「短标签 + 有符号数」；ASCII 负号，与现役 `P +N` 同字面）

| 值变化 | 浮字 | 默认颜色 |
|---|---|---|
| 伤害（效果/战斗） | `-N` | 红 |
| 战斗反击 | `↩-N`（保留反击记号，如需统一可去掉） | 红 |
| 回复 | `+N` | 绿 |
| 疲劳 | `疲劳 -N` | 红 |
| 攻击 ± | `P +N` / `P -N` | 绿/红 |
| 生命 ±（单位/角色上限） | `L +N` / `L -N` | 绿/红 |
| +1/+1、-1/-1 | `+N/+N` / `-N/-N` | 绿/红 |
| 护甲 / 圣盾 / 坚韧 / 复生 / 潜行 / 法术护盾 | `护甲 +N` 等 | 绿（获得）/红（消耗） |
| 毒素 / 冻结 / 紊乱 / 易损 / 反疗 / 沉默 / 失效 / 诅咒 | `毒素 +N` 等 | 红（施加）/绿（解除） |
| 荆棘（反噬层）/ 耐久 / 费用层 | `荆棘 -N` / `耐久 -N` / `费 +N` | 红/绿按极性 |
| 角色攻击（弹药） | `P +N` | 绿 |
| 指示物清除 | 每类一条 `护甲 -N`…（红/绿按极性） | 按极性 |
| 设为（Set） | 旧→新算差：`P +N`/`L -N`；差 0 不出 | 绿/红 |

### 3.4 颜色判定（不做「正数=绿」的机械判断）

```
增益 = （极性 Positive 且 增量>0） 或 （极性 Negative 且 增量<0）
减益 = （极性 Positive 且 增量<0） 或 （极性 Negative 且 增量>0）
中性 = 极性 Neutral / 差值为 0
```

- 伤害/疲劳恒红，回复恒绿（语义优先于符号）。
- 护甲被吸收：层数减少 → **红**（损失）；毒素被净化：层数减少 → **绿**（解除妨害）。
- 角色生命被设为更低 -> 红，更高 -> 绿。

### 3.5 豁免/去重规则

1. **伤害/回复不再与生命浮字重复**：`LifeChangeEvent` 只在「非伤害/非回复来源」时才浮字（给事件加 `LifeChangeCause`：Damage/Heal/Fatigue/LifeLoss/Modify/Set/Lifelink/Lock，按 Cause 分流）。
2. **离场不浮字**：换区清随离场，不出浮字；是否进日志由 P1 决定（默认只由「离场」行体现）。目标离场（`DeathExitStarted`）静默。
3. **回合末批量**（毒素发作/冻结倒数/衰退）只走汇总行，不上浮字（防一次冒十几条）。
4. **同目标同一步同文同值**只出一条浮字（例如两次 +1 合成 `P +2`；如需逐次审计则关掉该合并，见决策点 D5）。
5. **无战场锚不上浮字**：费用、临时元素、地牌槽上限、牌库/手牌数量 —— 走日志 + HUD 数字（HUD 的变色/跳动已有，本轮不扩）。

### 7.1 D6 · 4 个可观察写点怎么补（setter 方案备查）

**现状**：`Player.Life` 是公开读写属性（`Cards/Entity.cs:194-198`），全仓有十余处直接写（含建局/快照/死代码）：`player.Life -= amount`、`owner.Life += dealt`、`player.Life = value`、`player.Life = locked`…（`KeywordRules.cs:523,529,598`、`DamageAftermath.cs:190`、`StatGrantRouter.cs:37,42`、`FirstBatchEffectHandlers.cs:534`、`DamagePipeline.cs:619,623`、`Zones.cs:859` 等）。写操作本身不发事件，所以每个写入方都得自己记得补 `LifeChangeEvent`——G4/G5 就是这么漏的。

**setter 方案**＝把「写」收口到一个必须走的方法，用编译器逼所有人就范：

```csharp
public int Life { get => _life; private set => _life = value; }   // 断掉外部直写

public void ChangeLife(int value, LifeChangeCause cause, Entity source = null)
{
    int old = _life;
    _life = Math.Clamp(value, 0, MaxHealth);
    if (_life != old)
        Publish(new LifeChangeEvent { Player = this, OldLife = old, NewLife = _life, Cause = cause, Source = source });
}

internal void SetLifeSilent(int value) => _life = value; // 建局/快照/上限裁剪/生命锁
```

- **好处**：任何新增写点不传 `Cause` 就编译不过；战报/浮字/血条永远拿到准确的 `旧→新`，不会再出现「数值变了但没事件」。这是唯一能把「漏发布」从纪律问题变成编译问题的做法。
- **代价/风险**（也是我建议先不做的原因）：
  1. **事件顺序会变**：现役顺序是 `DamageEvent → CombatDamageEvent → LifeChangeEvent`；setter 发布发生在伤害结算内部的写点，会变成 `LifeChange` 先于 `CombatDamageEvent`，战报行序/触发器时点都要重新基线（V10、行流对拍、导出全受影响）。
  2. **一次伤害两次写**：`Life -= amount` 后还有生命锁 `Life = locked`；朴素 setter 会发两条（第二条仅在实际变化时），需要「钳制不发布」的事务位。
  3. **建局/读档噪音**：`ResetVitals`、快照回填、`DecreaseMaxHealth` 的内部裁剪必须静默，否则开局刷一串 LifeChange。
  4. 14 个写点 + 约 10 个引擎文件要与 P1/P2 的改动重叠，回归面大。
- **两种落法**：
  - **A（推荐，P1，已确认）**：处理 4 个可观察写点——**系命 2 处**（Legacy/Chain）补 `LifeChangeEvent`；**ModifyLife/SetLife 2 处不补事件**（已有 `StatModify/StatSet`，补了会重复），由 P2 订阅 + 刷血条。V10 断言：伤害/回复/流失各 1 例 → 恰 1 条 `LifeChange`；设置/修改各 1 例 → 恰 1 条 `StatSet/StatModify` 且**无**重复 LifeChange；系命 1 例 → 恰 1 条 `LifeChange` 且旧→新正确。不动事件顺序。
  - **B（彻底，建议单列 P4 之后）**：setter + `ChangeLife` + `PublishMode { Immediate, Deferred }`（伤害路径用 Deferred，保持 `DamageEvent → CombatDamage → LifeChange` 的现序），全量修十余处、重建 V10 基线。

> **决定（2026-11-13）：按 A 落地——只处理 4 个可观察写点（系命 2 处补事件、Modify/Set 2 处补订阅），不启用 setter 化。** B 作为独立任务备查，等 P1/P2 稳定后若仍想要「编译期强制」再评估；它解决的是「未来不再漏」，不是「现在补不齐」，而 A 的补点本来就是 P1 必做的。
